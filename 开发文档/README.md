# 开发文档（代码级实现文档）

> **定位**：记录**代码是怎么写的**——每个工程目录 / 模块 / 文件 / 函数的职责与演进。
> 与 `md/`（产品与架构**设计**文档）分工明确：
> - `md/` = 决策级、稳定、面向全员（产品 / 架构 / API / 页面 / 决策）
> - `开发文档/`（本目录）= 代码级、随代码演进、面向开发与维护
>
> **🔒 铁律：代码与文档同一次提交（代码文档并行）。改了代码就同步改文档。**

---

## 一、为什么单独一个文件夹（不放 md/）

- `md/` 是设计权威源，稳定且面向决策；塞进代码实现细节会让它膨胀、职责混乱。
- 代码文档的变更频率跟着代码走，独立目录便于随代码一起维护与审阅、也便于后续单独拆分仓库。

---

## 二、文档分两层（保证"每文件 / 每函数"都有文档，且不漂移）

### 层 1：代码内注释（唯一真源，永不漂移，**强制**）

- **文件顶部 header 注释**：文件职责、主要输入/输出、依赖、对应页面或接口 ID。
- **每个导出函数 / 类**：TSDoc（`@param` / `@returns` / `@throws` + 一句话作用）。
- 理由：注释与代码在同一文件里，改代码必然看到注释，不会脱节。

### 层 2：模块级 `.md`（结构与演进，放本目录）

每个后端 / 前端模块一份 `.md`，固定小节（见 §五模板）：职责 → 文件清单 → 对外接口 → 依赖 → 待优化 → 变更记录。

> 分工：**细粒度真相在代码内（层1）**，`.md` 只做**结构总览 + 演进历史**，不逐行复述代码，从而避免"文档追不上代码"。

## 三、目录结构

```
开发文档/
├── README.md              # 本文（规范 + 索引 + 模板）
├── 00-代码地图.md          # server/miniapp/app/admin 目录树 + 每目录一句话职责
├── 待办-外部凭据清单.md    # AppID/支付/域名 等待外部提供的凭据（提醒用）
├── server/                # 后端模块文档（每模块一份，随代码创建）
│   ├── _基础设施.md        # main / config / 响应拦截器 / 异常过滤器 / 静态服务
│   ├── auth.md
│   ├── favorites.md
│   └── ...
├── miniapp/               # 前端文档（核心 service / 组件 / 页面，随代码创建）
│   ├── services-indexLoader.md
│   ├── components-FullTrackPlayer.md
│   └── ...
├── app/                   # Android/iOS App 独立工程文档
│   └── README.md
└── admin/                 # 后台文档（P1）
```

> 约定：`server/{模块名}.md` 与 `server/src/modules/{模块名}/` **一一对应**；前端核心 service/组件/页面各一份，命名 `miniapp/{分类}-{名称}.md`。

## 四、更新时机（什么情况必须动文档）

| 触发 | 要更新 |
|:--|:--|
| 新增文件 | 对应模块 `.md` 的「文件清单」+ 文件 header 注释 |
| 改函数签名 / 新增导出 | 「对外接口」+ 该函数 TSDoc |
| 改依赖（库/表/接口） | 「依赖」小节 |
| 修 bug / 重构 | 「变更记录」追加一行（日期｜变更｜原因） |
