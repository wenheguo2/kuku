# 19 - 个性化点名故事设计方案

> **定位**: AI 原生差异化核心功能——家长输入孩子名字与偏好，实时生成一个"以孩子为主角"的专属故事并配音。这是巨头（真人配音、固定内容）**难以低成本复制**的能力，是酷酷的护城河与高价值付费钩子。
> **技术选型**: 故事文本 = **DeepSeek**（`deepseek-chat`，复用 `gen_v2_deepseek.py` 的调用方式）；配音 = **MiMo**（`mimo-v2.5-tts-voiceclone`，**直接复用 `dub_all.py` 逐句配音管线**）。
> **状态**: 设计方案 v1.0（待评审）｜ **规划归属**: MVP 后期试点 → Phase 2 主推
> **权威依赖**: 资产数量见 [08 §0.1](08-本地开发实施步骤.md)；养成护栏见 [13 号](13-陪伴养成系统设计.md)；API 口径见 [11 号](11-API接口文档.md)；内容审核走 AI 机审（决策 R6）。

---

## 0. 一句话价值

> **"每个孩子都想成为故事的主角。"** 把孩子的名字、喜好、要教的道理，变成一个当晚就能听的专属故事——用 AI 把"千人千面"的成本打到接近零。这是内容量优势之外，酷酷第二条护城河。

---

## 1. 三个核心决策（先定方向）

你提的三个问题就是本功能的命门，先给出**明确建议**，理由在后文展开：

| 决策 | 结论（建议） | 一句话理由 |
|:--|:--|:--|
| **① 内容策略**：新故事 or 改存量？ | **直接按输入生成全新原创故事（不用僵化模板，你已确认）** | 安全靠强 system prompt + 双重机审 + 家长预览兜底；专属故事是私有内容，风险面小，不必靠模板锁死 |
| **② 配音**：单音色 or 多音色？ | **默认多音色**——MiMo 单次只出一个音色，多音色靠**逐句配音 + 拼接**，而这正是你 `dub_all.py` 的现成做法 | 现有管线本就逐句配音，单/多音色**调用次数一样**，多音色几乎"白送" |
| **③ 生成时机**：实时 or 异步？ | **异步（30秒~3分钟）+「生成中」陪伴动画 + 完成推送；相同输入缓存复用；热门组合预生成** | TTS 是耗时/成本大头，异步体验最稳；缓存和预生成大幅降本 |

> **一条铁律**：**绝不把孩子名字塞进历史人物/名著/成语故事**——"朵朵让梨""朵朵砸缸"是灾难。点名只用于**原创虚构主角**的故事。

## 2. 输入设计（输入到底是啥）

### 2.1 输入字段

不是只有名字。要生成"对味"的故事，最小输入集如下：

| 字段 | 必填 | 作用 | 示例 |
|:--|:--:|:--|:--|
| **宝宝名字** | ✅ | 故事主角名 | 朵朵 / 张一诺 |
| **名字读音（拼音）** | ✅ | **TTS 读对名字的生死项**（多音字） | 朵朵 = duǒ duǒ |
| **小名/昵称** | ⬜ | 故事里更亲切的称呼（默认用名字） | 朵朵、诺诺 |
| **性别** | ✅ | 决定 他/她、主角设定 | 女 |
| **年龄段** | ✅ | 决定用词难度、故事长度、主题深浅 | 3-4 / 5-7 / 8-12 |
| **兴趣/喜好** | ✅ | 故事里的核心元素（多选或自填） | 恐龙、公主、汽车、太空 |
| **想教的主题** | ✅ | 故事内核（价值观/习惯）；前端给快捷选项+可自写 | 勇敢 / 分享 / 好好睡觉 / 不挑食 |
| **场景** | ⬜ | 睡前（安抚向）/ 日间（活泼向） | 睡前 |
| **陪伴角色** | ⬜ | 让 IP 角色（酷酷/桃子）当主角的好朋友 | 酷酷 |
| **特殊场合** | ⬜ | 生日/入园第一天等定制钩子 | 生日快乐 |

### 2.2 名字读音处理（重点，别踩坑）

中文名多音字极多（乐 lè/yuè、朝 zhāo/cháo、单 dān/shàn 作姓氏…）。**TTS 读错名字 = 家长最不能忍**。

- 输入名字后，前端用拼音库给出**读音候选让家长确认**（如"乐"→ ①lè ②yuè）。
- 存 `name` + `name_pinyin` 两个字段；配音时把读音以**自然语言指令**注入 `dub_all.py` 的 `user_msg`（如"主角名'乐乐'读作 yuè yuè"）——这正是现有管线处理多音字的方式（见 `get_subject_hint`），**无需 SSML**。
- 生僻字/英文名做兜底：无法注音时提示"我们会用 XX 读音，可修改"。

### 2.3 输入方式

- **引导式问答**（推荐）：一步一问（名字→性别年龄→喜欢什么→想让宝宝学会什么），像"填故事魔法卡"，符合儿童产品调性，也降低表单压迫感。
- **"想教什么"一步给快捷选项**（首批默认）：勇敢 / 分享 / 好好睡觉 / 不挑食 / 交朋友 / 上幼儿园 + "自己写"（直接生成支持任意主题，选项只是方便家长快选）。上线前优先把这几个主题的生成质量调好。
- 输入滥用防护见 §7.2（脏名字、他人真实姓名）。

## 3. 内容生成方案（DeepSeek）

### 3.1 直接按输入生成（核心方式，你已确认不用模板）

家长输入 → 拼装 prompt → DeepSeek **直接生成一个全新原创故事**，输出与现有 `segments.json` 同构的结构化 JSON。不套僵化模板骨架，让故事真正"按这个孩子、这些喜好、这个主题"来写。

- 复用你现有 DeepSeek 生成管线（`gen_v2_deepseek.py` 的调用方式：`deepseek-chat` + 结构化解析），把"批量造歌词"改成"单篇按输入生成故事 + 输出 segments 结构"（这就是你说的"故事生成脚本需要改改"的点）。
- 生成即产出**分段（segment）结构**，每段带 `character`（谁说的）+ `mood`（情绪）+ `text`——这是多音色配音与复用现有播放器的关键。

### 3.2 不用模板，安全靠什么（回应安全顾虑）

模板本是我为"安全"提的，你不想要——那安全用这四层兜住，同样稳：

1. **强 System Prompt 护栏**：固定角色（暖心儿童故事作者）+ 年龄用词表 + 字数区间 + **硬护栏**（无暴力/恐怖/成人/危险行为/过度说教；不得把孩子写成历史或名著人物）+ 输出 JSON 约束。参考你 `dub_all.py` 里 `get_subject_hint` 那种"把要求写死进 prompt"的成熟做法。
2. **结构化输出 + 校验**：强制 JSON，解析失败/字段缺失即重试或拒绝。
3. **双重 AI 审查（R6）**：生成后用 **DeepSeek 再过一遍**（换一套"安全审查" prompt，专查暴力/恐怖/成人/危险行为/价值观），命中即 `blocked` 不产出——同模型、不同 prompt，便宜够用。
4. **私有内容 + 家长兜底**：专属故事是**私有**的（只给这个家长，不进公开库），风险面天然比公开内容小；再加**家长预览 + 一键重生成 + 举报**闭环。

> **仍保留的一条硬护栏**：prompt 里明令**不得把孩子设成历史/名著人物**（避免"朵朵砸缸"式违和）——孩子永远是原创虚构故事的主角。

### 3.3 输出结构（复用现有 segments.json，直接接现有播放器/配音管线）

让 DeepSeek 输出**与现有 `segments.json` 同构**的 JSON，字段对齐 `dub_all.py` 实际读取的 `character`/`mood`/`text`：

```json
{
  "title": "勇敢的乐乐和小恐龙",
  "child_name": "乐乐",
  "theme": "勇敢",
  "age_band": "3-4",
  "moral": "遇到害怕的事，深呼吸、想办法，就不怕啦",
  "segments": [
    { "id": "sp_0001", "character": "旁白", "mood": "calm",  "text": "森林里住着一个叫乐乐的小姑娘……" },
    { "id": "sp_0002", "character": "酷酷", "mood": "happy", "text": "乐乐，别怕，我陪你一起！" },
    { "id": "sp_0003", "character": "乐乐", "mood": "brave", "text": "好，我们一起去！" }
  ]
}
```

- `character` → 交给 `assign_voices.py` 逻辑分配 `voice_id`（酷酷=V-TN-01、桃子=V-TN-04 已锁定；旁白=V-ADW-01；其余按性别/年龄从音色池选）。
- `mood` → `dub_all.py` 的 `MOOD_MAP` 直接吃（happy/brave/calm…）。
- 产出后：assign_voices → dub_all 逐句配音 → 合并 `full.mp3` → 落 OSS，**全程复用现成脚本**，接故事播放器 PL-01。

### 3.4 "改结局"玩法（可选交互）

- 可让 DeepSeek 一次生成 **2 个结局分支**，听到关键处让孩子/家长选——增加参与感；两个分支同样过机审。
- **不做**：改写经典/历史故事的结局（易失控、破坏原意）。

### 3.5 Prompt 要点

- **System**：角色 + 年龄用词表 + 字数区间（3-4岁≈300字 / 5-7岁≈600字 / 8-12岁≈1000字）+ 硬护栏 + **输出 segments JSON 结构约束** + 角色命名规范（旁白 / IP角色名 / 主角用宝宝名）。
- **User**：结构化输入（名字+读音+性别+年龄+兴趣+主题+场景+IP陪伴角色+特殊场合）。
- **温度**：0.7 左右（比批量造内容略低，保稳定与安全）。
- **兜底**：JSON 解析失败/超时→重试 1 次→仍失败给友好提示"再试一次"，不硬塞劣质内容。

## 4. 配音方案（MiMo，复用 dub_all.py）

### 4.1 多音色 = 现成能力（关键澄清）

你指出"MiMo 单次配音不支持多音色，需要拼接"——完全正确，而且**你的 `dub_all.py` 已经就是这么做的**：

- dub_all.py **逐句配音**：遍历 segments，每段按自己的 `voice_id` 用 `mimo-v2.5-tts-voiceclone` 单独合成一个 MP3，再由合并脚本拼成 `full.mp3`。
- 所以**单音色 vs 多音色，调用次数完全一样**（都是逐句）——多音色只是"每段用不同 voice_id"，**几乎零额外成本**。故建议个性化故事**默认就上多音色**（旁白 + IP角色 + 宝宝主角各一个音色）。
- 直接复用的现成能力：**voice_bank 音色库**（酷酷 V-TN-01 / 桃子 V-TN-04 锁定）、**assign_voices 分配逻辑**、**dedup 去重缓存**（相同 voice+text 不重复合成）、**MOOD_MAP 情绪注入**、**断点续跑**、**时长校验**（`is_bad_duration` 防 TTS 抽风）、50 并发 @ 300 RPM。

### 4.2 名字读对（复用 subject-hint 注入机制）

- 把主角名读音以**自然语言指令**拼进 `user_msg`，例如："本段主角名'乐乐'读作 yuè yuè，请读准。"——这正是现有管线处理多音字（"教"读 jiào）的同一机制，成熟可用，无需 SSML。
- 宝宝主角单独一个音色（童声池里按性别挑一个）；名字每次出现都靠指令锁读音。

### 4.3 父母声音克隆（你确认要加）

- **技术上零门槛**：dub_all.py 用的 `mimo-v2.5-tts-voiceclone` 本就是声音克隆模型——家长**录一段 MP3**，存进 voice_bank 当一个 `voice_id`，配音时旁白/某角色就用父母的声音，和现有逐句配音流程完全一致。
- **落地**：家长中心加"录制我的声音"入口 → 上传 MP3 → 生成该家庭专属 voice_id → 点名故事可选"用妈妈/爸爸的声音讲"。
- **必配合规**：①明确授权（本人声音、仅本账号用）；②禁止上传他人声音（防滥用）；③随账号注销删除声音样本；④加密存储。详见 §7。

### 4.4 降本（按你选的"直接生成"权衡）

- 你选了**直接生成**（每篇故事独一无二），跨孩子几乎没有可复用的句子——**dedup/拼接收益有限**。
- 结论：**MVP 直接整篇配音即可**（单篇仅 ¥0.2~0.6，配合"免费每周1个"完全可接受），不做拼接优化。
- 若未来成本变大，再考虑"复用故事骨架+只换名字句"降本（但那偏回模板方向，属权衡）。

### 4.5 凭据安全

- dub_all.py / gen 脚本里的 MiMo `api_key`、DeepSeek `AK` 目前是**明文**——上线须走 `.env`（对齐去密决策，见 v3 修订说明 §六 遗留项）。

## 5. 视觉方案（纯听，你已确认不做封面）

按你的决定，个性化故事**不生成封面**：

- **默认纯听**：走故事播放器 PL-01 的"纯音频"形态，用一个统一的**默认占位封面/主题色卡**即可，不为每个孩子生成图。
- **家长可选自传封面**：允许家长**自行上传一张图**作为该专属故事封面（如孩子照片/涂鸦）——零生成成本，还增强归属感。上传图需过**图片机审**（涉未成年人图像，注意隐私存储与注销删除）。
- **IP 立绘/场景**：本功能 MVP **不强制**用立绘；纯听即可。未来若做"立绘版"再复用现有 1,668 张立绘 / 54 张场景。

> 结论：**零新增美术**。纯听 + 默认封面（或家长自传），最省最快。

## 6. 技术架构与落地

### 6.1 生成任务流（异步）

```
家长输入 → 提交生成任务(POST) → 返回 task_id
   │
   ├─ 1. 输入校验/滥用过滤 + 名字读音指令生成
   ├─ 2. DeepSeek 直接生成故事 → segments.json（含 character/mood/text，自审）
   ├─ 3. DeepSeek 二次安全审查（R6：换"安全审查" prompt 再过一遍，不合规不产出）
   ├─ 4. assign_voices 分配 voice_id（酷酷/桃子锁定，宝宝主角配童声）
   ├─ 5. dub_all 逐句配音（含名字读音指令）→ 合并 full.mp3
   ├─ 6. 落 OSS，挂到 child_id
   └─ 7. 完成 → 推送/轮询通知家长
   前端：轮询任务状态或订阅通知；生成中显示“魔法故事制作中”陪伴动画
   复用脚本：gen（改造自 gen_v2_deepseek.py）→ assign_voices.py → dub_all.py → 合并脚本
```

### 6.2 与"CDN 静态"架构的关系

- 存量内容走 CDN 静态（不变）。
- **个性化内容是动态生成的**：生成后**落 OSS/CDN**（`personalized/{child_id}/{story_id}/`），一旦生成即变为静态资源，**照样走 CDN 播放**。只有"生成过程"是动态后端任务。

### 6.3 数据表（新增）

```sql
-- 个性化故事生成任务/成品
CREATE TABLE personalized_stories (
  id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  user_id BIGINT NOT NULL REFERENCES users(id),
  child_id BIGINT NOT NULL REFERENCES child_profiles(id) ON DELETE CASCADE,
  child_name VARCHAR(32) NOT NULL,          -- 敏感信息，随账号注销删除
  name_pinyin VARCHAR(128),
  gender VARCHAR(8), age_band VARCHAR(8),
  interests JSONB, theme VARCHAR(32), scene VARCHAR(16),
  input_hash VARCHAR(64),                    -- 缓存命中键（相同输入复用）
  status VARCHAR(16) NOT NULL CHECK (status IN ('pending','generating','review','ready','failed','blocked')),
  story_json_url VARCHAR(512),               -- OSS 上的 segments.json
  audio_url VARCHAR(512),                     -- OSS 上的 full.mp3
  cover_url VARCHAR(512),                     -- 默认占位或家长自传（可空）
  audit_result JSONB,                        -- AI 机审结果留痕
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  ready_at TIMESTAMP
);
CREATE INDEX idx_pstory_child ON personalized_stories(child_id, created_at DESC);
CREATE INDEX idx_pstory_hash ON personalized_stories(input_hash);
```

### 6.4 API（对齐 11 号 `/api/v1` 口径）

| 方法 | 路径 | 说明 |
|:--|:--|:--|
| POST | /api/v1/personalized/stories | 提交生成任务（body：child_id + 输入字段），返回 task_id |
| GET | /api/v1/personalized/stories/{task_id} | 轮询任务状态/结果 |
| GET | /api/v1/personalized/stories?child_id={id} | 该孩子的专属故事列表 |
| POST | /api/v1/personalized/stories/{id}/report | 家长举报不当内容 |
| DELETE | /api/v1/personalized/stories/{id} | 删除某条专属故事 |

- 播放复用现有故事播放器（PL-01），数据源指向 `story_json_url`/`audio_url`。
- **微信登录后自动建默认 child_profile**（对齐 18 号开工必读），否则专属故事无处归属。

## 7. 安全与合规（儿童产品重中之重）

### 7.1 儿童个人信息

- 孩子名字是**敏感个人信息**：最小化采集、**加密存储**、随**账号注销一并删除**（对齐 11 号 `DELETE /api/v1/user` 与 F-05）。
- 隐私政策明确告知"名字仅用于生成专属故事，不作他用"。
- **父母声音样本**（做声音克隆时）同属敏感信息：仅本账号使用、加密存储、随注销删除；上传须明确授权，**禁止上传他人声音**。

### 7.2 输入滥用防护

- **脏话/敏感词名字**：输入即过滤，拒绝生成。
- **他人真实姓名/名人**：不鼓励；至少做名人名单拦截。
- 频控：防刷（每账号每日提交上限）。

### 7.3 生成内容价值观安全（最高优先级）

- **双重 AI 审查（R6）**：DeepSeek 生成时自审 + **DeepSeek 换"安全审查" prompt 二次复审**，命中暴力/恐怖/成人/危险行为/价值观问题 → `blocked`，不产出。
- **家长预览 + 举报 + 重生成**：故事先给家长可预览/可重生成/可举报，形成人工兜底闭环。
- 抽审：定期人工抽查生成样本，回灌优化模板与 prompt。

### 7.4 版权

- L2 轻替换**严格排除**历史人物/名著/成语/真实作品；只替换原创虚构主角。
- MiMo 音色、DeepSeek 输出的**商用授权**须确认。

### 7.5 合规红线

- 守住**文娱非教育**（避双减）、**非游戏**（避版号）定位——个性化故事是"内容"，不引入对抗/闯关。

---

## 8. 商业化（这是强付费钩子）

个性化故事**天然是会员价值**，也是拉新裂变点：

| 玩法 | 免费用户 | 会员 |
|:--|:--|:--|
| 生成次数 | 每周 1 个（体验钩子） | 不限量 / 每日 N 个 |
| 音色 | 多音色（默认，本就零额外成本） | 多音色（默认） |
| 父母声音克隆 | ✗ | ✓（家长录一段 MP3，用爸妈的声音讲故事） |
| 特殊场合定制（生日等） | 限量 | ✓ |
| 保存/收藏 | 有限条 | 无限 |

- **裂变**：生成的专属故事可**分享给家人**（"听听朵朵的专属故事"）→ 低成本获客（呼应"获客是第一生死线"）。
- **成本测算（需实测校准）**：DeepSeek 单篇文本 ≈ 几分钱；MiMo 配音是大头，单篇 3 分钟约 ¥0.2~0.6。**免费每周 1 个** → 单用户月成本约 ¥1~2，可控；dedup 去重（现成）+ 含名字句拼接 + 预生成可进一步降本。
