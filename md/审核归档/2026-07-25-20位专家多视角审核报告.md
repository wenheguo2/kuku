**✅ 优点**

**⚠️ 问题**
1. 大量内联 style 写死色值（如 `challenge/index.tsx` 里 `#7FC96A`、`#E4572E` 直接硬编码），绕过 CSS 变量/design-tokens——夜间模式下这些硬编码色不会随主题切换，存在暗色底+亮色字对比度隐患。
2. px 与 rpx 混用：页面内联样式多用 px（`fontSize: '34px'`），SCSS 用 rpx，缩放行为在不同机型不一致。
3. `member`、`comprehensive` 等页大量布局直接内联，无法被设计走查工具静态审计。

**💡 建议**：定一条"展示色值必须走 CSS 变量"的硬规则，把 `design-tokens.json` 生成 SCSS 变量文件单源引用；内联样式收敛进 `.scss`。

## 四、后端架构师（NestJS）

**✅ 优点**
- 模块化清晰（12 模块 12 表），守卫链路正确：JwtAuthGuard（填 user）→ RateLimitGuard → VipGuard。
- `markPaid` 事务 + 订单行锁 + 用户行锁双重串行化，幂等续期正确；`addMonths` 月末钳制正确；`children.remove` 事务内悲观锁防 TOCTOU；`TestStore.take()` Lua 原子领取防双提交——历史 P1 竞态问题全部确认已修。
- 启动环境门禁（`environment.validation.ts`）fail-closed：release 强制强 JWT_SECRET、真支付凭据、非 draft 协议版本，防"配置遗漏上线"。
- `PUT /user/profile` 空 body 已短路（历史低危项已修）。

**⚠️ 问题**
1. **业务日志几乎为零**：仅 TestStore/Wechat/异常过滤器有日志，订单创建、会员开通、账号注销、协议撤回等关键操作无审计日志，出问题无法追溯（儿童产品的数据删除操作尤其需要留痕）。

**💡 建议**：加一个轻量 `AuditLogInterceptor`（写操作入 events 或独立表）；死字段随下一次 schema 变更一并清理。

## 五、数据库架构师

**✅ 优点**
- BIGINT 主键映射 string 防精度丢失；复合索引按查询路径设计（`(child_id, subject, current_stage)` 等）；`synchronize=false` + schema.sql 单一建表基线，纪律好。
- 外键策略有思考：child 级联删除带走成长数据，events.child_id 故意不级联（应用层置空保留埋点）。

**⚠️ 问题**
1. 无迁移工具链：schema 演进靠 SQL 注释里的"已建库升级（本地执行一次）"手工语句（schema.sql L103-107），多环境部署时极易漂移——建议引入 TypeORM migration 或至少一个 `migrations/` 有序 SQL 目录。
2. `orders.amount` DECIMAL 在 entity 中为 string，`toDto` 用 `Number(o.amount)` 转回——金额链路建议统一"分"为单位的整数，避免浮点渗入。
3. `events` 表无归档/分区策略，埋点只进不出，上量后单表膨胀。
4. `play_history.trim` 的 OFFSET 子查询删除在高并发下可能与 UPSERT 交错（可接受但应知晓）。
