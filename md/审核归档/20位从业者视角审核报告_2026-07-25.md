## 1. 产品经理视角

**反馈**：文档体系是同类项目中少见的完整——00-20 号文档覆盖产品/技术/合规/运营全链路，README 建立了「权威口径表」防止跨文档漂移，05 号 84 项决策编号化，这套治理值得肯定。三大支柱（故事/歌曲/教学）+ 四级朋友养成的产品骨架清晰。

**问题分析**：
1. **O-1 开口项悬而未决**（00 §7.1）：故事/歌曲的免费/付费边界"上线前再定"，但这直接影响首页/列表/播放器的锁定态 UI 与转化漏斗设计，拖到上线前定会引发返工。
2. **文档编号断档**：17 → 19 跳号（18 已并入 20），README 有说明但新人易困惑。
3. **MVP 排期风险**：00 §9 写 Phase 1 为 4-6 周，但内容资产多项仍在生成中（整曲 MP3、timeline.json、LRC 均标 ⏳），且微信支付真实通道未接（stub），MVP 定义与资产就绪进度之间没有明确的「内容就绪门槛」。
4. **搜索体验预期未定义**：MVP 用 PG 全文检索（README 三.94），但没有定义"搜不到"时的产品兜底（推荐/热词/纠错）。

**建议**：
- 把 O-1 提级为本周决策项，先定粗粒度规则（如"每学科前 N 篇免费"），细则可后调。
- 在 04 号里增加「内容就绪门槛」：MVP 上线要求哪些学科的整曲 MP3/LRC/timeline 达到 100%，未达标学科先隐藏入口。
- 搜索空结果页给"猜你想听"推荐位（复用 _home.json 热点池）。

## 2. 儿童教育专家视角

**反馈**：识字 3,499 字 / 英语 3,910 词 / 拼音 100 课的量级设计合理，"学习1/2/3 三个独立复习角度"符合多通道重复记忆规律。「只升不降、答错无惩罚、无限重试」（13 §3.3）对低龄儿童的心理保护非常到位。

**问题分析**：
1. **已下线间隔复习是教育效果的损失**：13 号明确下线了间隔复习/久别重逢机制（为合规与温柔化让路）。从记忆曲线角度，识字类内容不做任何形式的复现提示，长期留存率会显著下降。
2. **3-12 岁跨度过大而无分层路径**：00 §3.1 划了 L1-L6 分级标识，但项目已明确排除年龄分级过滤，所有内容对所有孩子平铺。5 岁孩子可能刷到 9-12 岁的长篇章回，认知负荷不匹配。
3. **综合挑战"识字 1X+3-9X 全对"标准偏严**（00 §4.3）：对 6-7 岁儿童一次全对的通过率会较低，虽无惩罚，但反复不过仍可能挫伤积极性。
4. **拼音无习题**（00 §4.3），意味着拼音学科的"好朋友/好伙伴"晋升路径缺失，孩子的拼音进度在朋友收集册中会永远停在"已相识"，体系不自洽。

**建议**：
- 不恢复"复习任务"，但可用**内容推荐**变相实现间隔复现：在故事推荐池里提高"包含孩子已相识字词"的内容权重（叙事上仍是"再听一个故事"，不构成教育评测）。
- 首页/列表按 L1-L6 做**软排序**（不做硬过滤，不违反排除项）：孩子档案虽无年龄字段，可按收听行为推断偏好长度。
- 明确拼音学科在收集册中的口径：要么定义"收听即好朋友"的特例，要么在收集册筛选中隐藏拼音的 2/3 级。

## 3. 儿童心理学家视角

**反馈**：「交朋友」叙事替代「测试/掌握度」是非常好的设计——把外在评价转为社交隐喻，符合 3-8 岁儿童的泛灵心理。虚线剪影"再听 1 个故事遇见"（components-guide 8.3）用悬念而非焦虑驱动，纯展示型贴纸无兑换、不打卡不连续天数，避免了行为成瘾设计，专业水准很高。

**问题分析**：
1. **会员门控与儿童情感的冲突点**：朋友收集册查看是会员专属（13 §6）。孩子交到了朋友却"看不到自己的朋友"，锁定预览对儿童是一种情感剥夺体验——转化钩子作用在家长身上，但挫败感落在孩子身上。
2. **综合挑战失败的即时反馈未见规范**：文档规定"答错无惩罚"，但未规定失败时的**话术与视觉**（如是否出现红色❌、"错了"字样）。对低龄儿童，负向视觉符号本身就是惩罚。
3. **睡前模式与内容匹配**：夜间主题（N-01）视觉做得很好，但未见"睡前内容过滤"逻辑——睡眠定时开启时若播到"放声大笑"类兴奋内容，与助眠目标冲突。

**建议**：
- 收集册免费用户至少可看**汇总数**（"你已交到 23 个朋友"），仅明细/徽章墙锁定，把情感基本盘留给孩子。
- 在 13 号补一节「挑战反馈话术规范」：答错用中性色 + "再想想/换一个"类话术，禁用 ❌/红色/哭脸。
- 睡眠定时激活时，续播队列自动切换到摇篮曲/冥想放松/自然音效池。

## 4. 法务/合规顾问视角

**反馈**：15/17 号文档对类目（文娱非教育非游戏）、双减红线、游戏化红线的把握准确；监护人同意留痕、child_id 越权 404、账号注销接口已落地，代码层面的合规基础好于多数同阶段项目。

**问题分析**：
1. **协议三件套仍是 draft**（server/.env.example L55-57：`2026-07-draft`）：隐私政策、用户协议、儿童个人信息保护规则未经法务定稿即不可上线，release 门禁虽已设，但**法务定稿本身没有排期与责任人**。
2. **版权明确风险项未闭环**：《波普先生的企鹅》（合著者 Florence Atwater 保护期至约 2029 年）仍在 K4 库中须删除或授权；《小熊维尼》文本虽公版但与迪士尼视觉 IP 强关联，需改名/规避品牌元素。此两项在 15 §3"内容来源与版权"勾选项下没有对应的处置记录。
3. **AI 生成内容标注**：15 §3 有勾选项，但 miniapp 页面中未见"内容由 AI 生成"的展示层标注实现——《生成式 AI 服务管理办法》要求显著标识。
4. **功能排除项的合规残余风险**：项目明确不做家长锁/支付验证，但 15 §6 又要求"未成年人支付限制与退款机制"。微信支付对儿童类目审核偏严（17 §5.3），无任何监护人支付确认的会员购买流程，存在被平台驳回或事后退款纠纷的风险，此矛盾需要书面决策留痕。
5. **第三方 SDK 清单**（15 §5 未勾选）：隐私政策必须列明微信登录、支付、TTS 等第三方数据流向，目前无清单。

**建议**：
- 本周给协议定稿排死线，法务未定稿前 RELEASE_MODE 保持 false 的门禁不动。
- 立即从内容库物理删除《波普先生的企鹅》并留删除记录；《小熊维尼》改名（如"小熊噗噗"）+ 封面规避红衣形象，法务复核后归档。
- 在 App 简介页与故事详情页脚注加"本内容由 AI 生成"标注；这是低成本高优先级项。
- 就"无监护人支付确认"出一页风险决策书（谁拍板、依据什么），归入 05 号决策清单。

## 5. UI/UX 设计师视角

**反馈**：design-tokens v4.0「典藏绘本·日夜双主题」完成度高：夜灯金/深夜蓝的睡前氛围、鎏金书匣会员页、四级朋友色经 Color Oracle 色盲验证、禁 emoji 占位改真实资产管线——这套设计语言有辨识度且工程可落地（tokens 与 HTML :root 单一数据源）。

**问题分析**：
1. **HTML 设计稿与 README 屏数口径不一**：README 文档清单写"26 屏"（酷酷UI设计稿.html），UI设计方案/v4 版写"24 屏"，且 README 链接的文件名是 `酷酷UI设计稿.html` 而实际文件是 `酷酷UI_融合版_v4.html`——链接会 404。
2. **横屏教学播放器的进入/退出体验未定义**：PL-03 强制横屏，但从竖屏课程列表 → 横屏播放器的旋转过渡、以及儿童误触返回的确认策略在 09/UI 方案中均未见规范。
3. **文字 TabBar 与设计稿冲突**：app.config.ts 注释写"文字 Tab（无需图标资源即可运行）"，虽启用了 custom TabBar（SVG），但兜底 list 无 iconPath，若 custom 组件加载失败会退回纯文字 Tab，与设计稿差异大。
4. **body 20px 与 accessibility.bodyFontSize 18px 不一致**：typography.body=20px，accessibility.bodyFontSize=18px，两个 token 语义重叠易被开发混用。

**建议**：

- 在 UI设计方案补 PL-03「横屏进出规范」：进入前 toast 提示旋转、返回二次确认（儿童误触率高）。
- 给 tabBar.list 补齐 iconPath 兜底图标。
- 合并或注释区分 body/bodyFontSize 两个 token 的适用场景。

## 6. 前端工程师（小程序）视角

**反馈**：代码质量整体在线：api.ts 统一包络解析 + 401 重定向去抖、audioPlayer 单例区分 weapp BackgroundAudioManager 事件只绑一次（避免换曲累积监听）、zustand 已改逐字段 selector 订阅、storage 统一 Taro API（无 localStorage 误用）。注释密度和中文注释规范一致性好。

**问题分析**：
1. **M-4 未修（已知遗留）**：story/player 的 onEnded 绑定页面生命周期，离开播放页后曲终无 handler → 自动续播中断且 isPlaying 残留。endedDriver 机制已存在（audioPlayer.ts L26），但页面级 onEnded 与 App 级驱动的职责边界未迁移完。
2. **注释与实现矛盾（已知 R1-1/R1-2）**：progress 相关头注释与 comprehensive/challenge 页面注释仍残留"回落/给1次重试"字样，实现已是"只升不降·无限重试"，comprehensive/index.tsx 还有一处**用户可见文案**说"回落"——这是直接面向家长的错误信息。
3. **BackgroundAudioManager 的 `!autoplay` 分支不可靠**（audioPlayer.ts L48-50）：设置 src 后自动播放，随后立即 pause 存在竞态（部分机型 pause 早于播放开始会失效），产生"点了不想播却响了一声"的体验缺陷。
4. **api.ts 无重试与网络异常分类**：Taro.request 抛出的网络层异常（断网/超时）未被 catch 转成友好提示，页面各自处理不一致。
5. **无前端测试**：miniapp 仅有 type-check 脚本，无 jest/vitest；stores 的纯逻辑（进度、队列）完全可测而未测。

**建议**：
- 优先修 M-4：把曲终续播全部收敛到 App 级 endedDriver，页面 onEnded 只做 UI 更新。
- 全局 grep"回落/1次重试"清掉三处注释 + 一处文案（半小时工作量，消除合规话术隐患）。
- weapp 分支 autoplay=false 时改为延迟到 onCanplay 后 pause，或干脆约定 weapp 下不支持非自动播放加载。
- api.ts 包一层 try/catch 区分 `request:fail` 网络错误，统一 toast"网络不给力"。
- 给 stores/utils 补 vitest 单测（不依赖 Taro 运行时的纯函数先行）。

## 7. 后端工程师视角

**反馈**：NestJS 工程结构规范（12 业务模块 + 13 实体 + 全局管道/过滤器/拦截器），markPaid 已加事务+行锁、page_size 已设上限、JWT 错误文案侧信道已修，schema.sql 作为权威 DDL 随 dist 打包（nest-cli.json assets）细节到位。

**问题分析**（含已知低危遗留复述 + 新增）：
1. **PUT /user/profile 空 body → TypeORM 500**：ValidationPipe whitelist 后空对象直达 repository.update 抛异常，应返回 400。
2. **favorites/history 非原子写**：读-改-写模式在并发收藏/取消时可能丢更新。
3. **addMonths 月末溢出**：会员续期 1/31 + 1 月 → 3/3 类错误，用户实际少/多得会员天数，属资损类 bug。
4. **learning_progress.retry_used / last_test_failed 死字段**：无限重试决策后成僵尸列，误导后续开发。
5. **admin 与用户共享 JWT_SECRET**：用户 token 与管理员 token 同密钥签发，理论上伪造横向风险；应拆分 ADMIN_JWT_SECRET。
6. **支付 stub 与真实通道的切换面未收口**：ALLOW_PAYMENT_STUB=true 下单直接成功，微信支付 V3 回调验签/幂等/退款接口完全未写，这是 MVP 最大的未完成面（17 号 R3 决策要求支付进 MVP）。
7. **静态资源鉴权缺失**：ServeStaticModule 把 production/ 全量暴露在 /static 下，会员专属内容（蒙学/诗词/大IP 音频）无 URL 鉴权，知道路径即可免费听——会员模型形同虚设。题库 verify.json 的 answer 泄露同源于此（服务端判分虽已做，但原始文件仍可直读）。

**建议**：
- 修 1-4 号小项（各 <1 小时），删死字段并迁移 schema。
- 新增 ADMIN_JWT_SECRET 并在 release 校验非空。
- 会员音频改走带签名的临时 URL（后端签发 5 分钟 token 的 302，或上 CDN 后用 CDN 鉴权），/static 只留免费内容与索引；verify.json 移出静态目录。
- 支付通道给出明确排期：V3 下单/回调验签/幂等表/退款四件套，回调必须校验金额与订单状态机。

## 8. 安全工程师视角

**反馈**：安全基线动作齐全：安全响应头子集、请求体 1MB 限制、TRUST_PROXY 注释了 XFF 伪造风险、scrypt 管理员口令、release 模式强制关 mock/stub、越权统一 404 不泄露资源存在性。能看出经过多轮安全审查。

**问题分析**：
1. 🔴 **TTS API Key 明文入库**：`config/tts_providers.json` 中 MiMo key（tp-cytm...）明文存在且该文件在 git 建议提交清单内（.gitignore L105 "config/ 配置（脱敏后）"——实际并未脱敏）。任何拿到仓库的人可盗刷 TTS 额度。**这是全项目最高优先级安全问题。**
2. 🔴 **admin_token 存 localStorage**（admin/Login.vue L43、api/index.ts L12）：后台一旦引入任何含 XSS 的依赖或富文本，token 直接被窃取。管理后台权限=全量内容与用户数据。
3. 🟠 **登录接口无速率限制证据**：admin/auth/login 未见节流/锁定策略，admin123 弱默认口令 + 无限爆破 = 高危组合（虽 release 强制 scrypt，但爆破限制与口令强度是两回事）。
4. 🟠 **JWT 7 天有效期无吊销机制**：登出仅清客户端，服务端无黑名单/版本号，被窃 token 7 天内持续有效。
5. 🟡 **CORS 开发态 origin:true + credentials:true**：开发环境组合宽松，若误带到准生产会成为 CSRF 面。

**建议**：
- **立即轮换 MiMo key**（已泄露即作废），新 key 移入 .env；若 git 历史已含该文件需 filter-repo 清历史（git 操作由您自行执行，此处仅给方案）。
- admin 改 httpOnly + SameSite=Strict cookie，或至少 sessionStorage + 短有效期（当前 8h 可缩到 2h）。
- auth 两个 login 接口加 Redis 计数节流（如 5 次/分钟/IP + 账号级锁定）。
- users 表加 token_version 字段实现登出即吊销（低成本方案）。

## 9. 测试/QA 工程师视角

**反馈**：14 号 AI 用户体验测试方案是亮点——用 AI 模拟用户走查合规话术断言，把"展示层 0 处教育评测词汇"变成可执行门控。server 有 jest + e2e 骨架。

**问题分析**：
1. **测试资产与产品复杂度严重不匹配**：server 仅 app.e2e-spec 示例级用例；miniapp/admin 零测试。判分规则（识字/英语/拼音三套通过标准 × 普通/综合两级 × 直接挑战路径）是组合爆炸的核心逻辑，目前全靠手工回归。
2. **无 CI**：无任何流水线配置，type-check/lint/test 全靠自觉，回归风险不可控。（按团队约定，CI 平台接入方案仅供参考、不代为落地。）

## 13. 音频工程师视角

**反馈**：整曲 MP3 + timeline.json 二分定位的方案（02 决策2）在体验与成本间平衡得好；播放器对 weapp BackgroundAudioManager 的单例复用、metadata（title/epname/cover）填充规范；睡眠定时基于 deadline 而非 duration，跨页面稳。

**问题分析**：
1. **音频失败无降级**：onError 只 toast"稍后重试"，无自动重试（哪怕一次）、无切备用 URL、无失败上报——CDN 单点抖动会直接转化为用户流失。
2. **无响度一致性规范**：多 TTS 引擎（MiMo/dashscope）+ MiniMax 歌曲混合产出，未见 LUFS 响度归一要求；孩子睡前从 -14 LUFS 的故事切到 -8 LUFS 的歌曲会被吓醒，这是儿童音频产品硬指标。
3. **seek 在 weapp 后台管理器上的精度问题未标注**：BackgroundAudioManager 的 seek 在部分安卓机型有 ±1-2s 偏差，教学播放器依赖 timeline 精确定位段落，偏差会导致立绘/字幕错位。
4. **码率策略未定义**：18 万+ MP3 的码率/采样率规范未见文档化，直接影响 CDN 成本与弱网体验。

**建议**：
- onError 加一次 2s 退避自动重试 + play_error 埋点。
- 生产管道加 loudnorm（EBU R128，目标 -16 LUFS 语音 / -14 LUFS 歌曲）批处理，新增内容强制、存量分批。
- 教学播放器段落定位改为"seek 后以 onTimeUpdate 实测值校正当前段"，不信任 seek 结果。
- 文档化码率标准（建议语音 48kbps mono / 歌曲 96-128kbps）。

## 20. 投资人/商业分析师视角

**反馈**：这是一个「AI 一人公司」模式的极致样本：18 万段内容、6 千歌曲、1,600 张立绘的边际成本趋近于零，内容资产的生成能力本身就是壁垒；文档治理水平（权威口径表、决策编号）说明组织能力可复制、可审计。三端代码已具雏形，不是 PPT 项目。

**问题分析**：
1. **收入模型单一且未验证**：100% 依赖会员订阅，无任何真实支付跑通记录（stub），LTV/CAC/转化率全部是假设；儿童内容赛道会员转化率行业均值 2-5%，按此测算需要相当规模 MAU 才能覆盖 CDN+服务器成本，敏感性分析缺失。
2. **平台依赖风险**：营收与获客 100% 绑定微信生态，类目政策（儿童+付费）是审核重灾区，单点政策变化即致命；APP（P1）是对冲但排期在会员验证之后，顺序有争议。
3. **合规负债清单影响交易**：明文 API key、协议未定稿、版权两项未闭环、无监护人支付确认——尽调中每一项都是减分项，且都属于"花小钱就能修"的低级负债。
4. **内容质量的护城河存疑**：AI 量产能力竞品 6 个月可复制，真正的壁垒应是「角色 IP + 个性化点名 + 孩子的成长数据」，但点名故事排在 P2、IP 运营无规划。
5. **关键人风险**：一人公司模式下，生产管道/密钥/运维知识全在一人脑中，无交接文档。

**建议**：
- 上线后 30 天内跑通「真实支付 + 100 个付费用户」的最小验证，拿到真实转化率再谈扩张。

## 结语

**共识判断**：项目的产品设计（陪伴养成合规叙事）、文档治理、内容资产规模均达到超出阶段预期的水准；三端代码是真实可运行的工程而非原型。**当前最大风险不在"做得不够多"，而在少数"低级但致命"的负债项**——明文密钥、协议未定稿、静态目录裸奔、支付未闭环。这些项修复成本极低，但任何一项带上线都可能造成不可逆损失。建议按 P0 → P1 顺序在两个迭代内清零，再进入增长动作。

> 本报告基于 2026-07-25 仓库快照；历史已修复项（markPaid 竞态、page_size 上限、JWT 侧信道等）已核实不再列入。
