| 目录 | 体积 | 必传？ | 说明 |

- **客户端取址**：`staticBaseUrl`（构建时注入）→ 方案A=`https://cdn.你的域名`；方案B=`https://你的域名/static`。其下必须能访问 `index/`、`illustrations/`、`audio/`、`generated_stories/` 四个顶层目录。

### 3. 小程序端（不在服务器，构建注入）

- `miniapp/` 本地构建 → `dist/`（含真实 AppID + 真实域名）→ 微信开发者工具上传体验版 → 提审发布。

### 4. 域名/证书/白名单（不"上传"但必须配置）

| 项 | 配置 |
|---|---|
| `api.你的域名` | ICP 备案 + certbot HTTPS + Nginx 443→3000 反代 |
| `cdn.你的域名`（方案A）/ `你的域名`（方案B） | ICP 备案 + HTTPS + 微信 downloadFile 白名单 |
| 微信 request 白名单 | `https://api.你的域名` |
| 微信 downloadFile 白名单 | 方案A `https://cdn.你的域名` / 方案B `https://你的域名` |
| 管理后台（可选） | `admin.你的域名` + CORS_ORIGINS 放行 |

## 三、发现的问题与建议（按优先级）

### 🔴 D1. 450GB 上传的现实成本未量化（建议执行前补充）

**位置**: 03 §3.2、04 §5

文档说"450GB 会传很久，预留数小时"——但按家庭宽带上行实测估算（50Mbps ≈ 6MB/s），450GB 需要 **~21 小时** 连续上传；20Mbps 上行则需 **~2 天**。且断点续传虽可重跑，但中途网络波动会反复补传。

**建议**：
1. 明确**分批上传顺序**：第一批 `index/` + `illustrations/`（~4GB，分钟级，先让页面/封面可用）→ 第二批热门学科音频 → 第三批其余音频（后台慢慢传）。
2. 上传期间**不要发布小程序**，否则用户会大量 404（audio 未传全）。
3. 在 04 验收清单增加 **"全量音频抽查可播"** 项（如每学科抽 3 个故事 + 全部整曲 URL 探测），而非只查"域名在白名单内"。

### 🔴 D2. 模式1（先上线暂不卖会员）下，会员购买入口的处理未定义

**位置**: README §3、02 §3.3

模式1 推荐方案（`NODE_ENV=development` + `ALLOW_PAYMENT_STUB=true`）意味着：**用户点"开通会员"会走 stub 假支付**。文档说"点确认开通走 stub 提示"（04 §5 验收项），但未说明前端入口要不要隐藏/禁用。

**风险**：如果按此模式公开发布，真实用户看到"升级会员→立即开通→(假支付/失败提示)"，体验很差，且微信审核可能对"不可用支付按钮"提出质疑。

**建议**：
1. 模式1 上线时，前端会员入口**改为"敬请期待/即将上线"态**（或隐藏开通按钮，仅展示权益对比）。
2. 或者明确"模式1 仅限内测，不公开发布"；公开发布必须走模式2（支付真实对接后）。
3. 在 04 验收清单增加对应检查项。

### 🟡 D3. 静态资源 URL 的中文路径编码依赖前端，上传时需验证

**位置**: 03 §3.5、04 §5

文档已注明"小程序端由 path.ts 自动编码，无需手工处理"，且 `utils/path.ts` 逐段 encodeURIComponent 支持中文。但 **COS/OSS 桶内是否保持中文原名**取决于上传工具行为（coscli 默认保留，某些工具可能转义）。建议验收时用 `curl -I "https://cdn.你的域名/…中文路径…"`（URL 编码后）实际验证 200，文档 03 §3.5 已有示例——保持执行即可。

### 🟡 D4. 模式2（卖会员）的依赖链未闭合

**位置**: README §3 支付说明、02 §3.3

模式2 需要"先完成微信支付 v3 对接（开发任务，本文档范围外）"。这意味着**文档集本身不能支撑"带真实会员的完整上线"**——若用户选择卖会员，还需要一份支付对接文档（统一下单/回调验签/幂等/退款）。文档对此有诚实标注（"不是零改码"），属已知缺口，建议补一份 `06_微信支付对接.md` 或在 00 待办中排期。

### 🟢 D5. 备份初始建立时机可提前

**位置**: 02 §1.5 建议建立习惯、04 §6.1 给 crontab

02 只给了手动备份命令，crontab 自动化在 04 §6.1 才出现。**建议 02 阶段就把 crontab 备份配好**（上线前就有数据了，早备份早安心），04 的每日备份验收提前到 02 验收项。

### 🟢 D6. 监控告警依赖云厂商手动配置，无文档步骤

**位置**: 04 §6.2

04 §6.2 建议"云监控对 /health 做拨测告警"，但未给具体配置步骤（不同云厂商操作不同，可理解）。建议至少明确：**微信小程序后台没有宕机告警**，上线初期至少每天看一次 pm2 logs + 云监控 CPU/带宽，或加一个简单的定时 curl 脚本（crontab 每分钟 curl /health，失败发邮件/钉钉）。

## 五、结论

**这份文档集足以支撑一个人按步骤完成部署上线**（模式1：内容可用、会员待接入）。三个关键动作：

1. **按 01→02→03→04 顺序执行**，每篇验收全绿再进下一篇；
2. **方案 A 先行**（对象存储+CDN），服务器规格小、全国访问快；
3. **上线前补上 D1 的分批上传计划 + D2 的会员入口处理**，其余 D3-D6 为可选的完善项。

**最需要你决策的一件事**：模式1（先上线不卖会员，stub 提示）还是等支付对接完再上（模式2）？文档推荐模式1，但需要配套"前端会员入口降级"的处理方案——我可以帮你把这个方案补进文档，或者直接在代码里实现。
