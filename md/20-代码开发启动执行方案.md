### 1.3 ⚠️ 契约校准点（开工前必读）

- **真实 `_global.json` 的 `subject_id` = 中文学科名**（如 `"上下五千年"`），字段为 `{schema_version, index_type, generated_at, stats:{total_subjects,total_entries}, subjects:[{subject_id, subject_name, category_count, total_entries, cover:{cover_image_url, cover_level}}]}`；`cover_image_url` 为**相对路径** `covers/generated/{学科}/{学科}.webp`。

- **✅ 决策（两种方式对比后）：前端直接消费真实索引结构（保留中文 `subject_id`/`path`），不重构为字母 ID。**
  - **方式A（采用）**：吃真实中文结构。物理目录（audio/covers/segments）本就全中文，索引与之一致，**零重构**；唯一缺点是“中文入 URL”，用统一工具 `buildAssetUrl(path)` 对每段 `encodeURIComponent` 即可干净解决。
  - **方式B（不采用）**：重构索引为字母 ID（A/B/C）。看似 URL 更干净，但物理目录仍是中文 → 需额外维护一套“字母 ID ↔ 中文路径”映射用于每次媒体取值，**复杂度不降反升**，还要重跑 06/09 覆盖 18 万+ 条目、并触及 §9.4 的改名遗留，风险大收益小。

## 3. 落地执行序列（本地优先，按依赖分 4 批）

> 每批都有明确产出与验收，**做完一批验收通过再进下一批**。命令与 SQL 细节以 08 号为准，本文只给序列与关键约束。

### Batch 1：后端骨架 + 数据库（零内容依赖，第一优先）

**目标**：`server/` 能 `npm run start:dev` 起在 3000，连上 PG，静态资源可访问，健康检查通过。

1. **建库建表**：按 [08 §2.1/§2.2](08-本地开发实施步骤.md) 在本地 PG 建 `kuku_stories` + **12 张表 + 全部索引**，跑 §2.3 验证 `\dt` = 12 张表。
2. **NestJS 初始化**：`npx @nestjs/cli new server`（`--package-manager npm --skip-git`），安装 `@nestjs/typeorm typeorm pg @nestjs/config @nestjs/jwt @nestjs/passport passport-jwt @nestjs/serve-static`。
3. **基础设施代码**：
   - `.env`（`DB_* / REDIS_* / JWT_SECRET / STATIC_ROOT=../production / PORT=3000`，**不入库**）；
   - `database.config.ts` 连 PG，`synchronize=false`（表已由 SQL 建好，实体只做映射）；
   - `ServeStaticModule` 映射 `production/` → `/static`（替代 CDN）；
   - 全局：`/api/v1` 前缀 + 响应拦截器统一 `{code,message,data}` + 异常过滤器。
4. **TypeORM 实体**：12 张表各建一个 entity（仅映射，不建表）。

**验收**：
- `GET http://localhost:3000/static/index/generated_stories/_global.json` 返回 JSON；
- `GET http://localhost:3000/api/v1/health` 返回 `{code:0}`。

### Batch 2：后端 MVP 接口（按 08 §4.4 优先级）

**目标**：登录→自动建默认孩子档案→收藏/历史/埋点/进度全链路 CRUD 通。

## 8. 工程规范决策（本轮确认）

### 8.1 技术栈（沿用 04 §8.1 KD 决策，无新增）
一句话：**Taro 3 (React + TS) 一套代码编译微信小程序 + iOS/Android APP + H5**，正是“小程序/APP 都要”的最优解（KD-01）。后端 NestJS + TypeORM + PostgreSQL 15 + Redis；状态 Zustand(端)/Pinia(后台)；样式 SCSS；后台 Vue 3 + Element Plus。

### 8.2 代码组织：强模块化（改问题不互相牽连）
- **后端**：NestJS 按 feature module 隔离，每模块自包含 `controller/service/dto/entity/module`。改「收藏」的 bug 只动 `modules/favorites/`，不牽连其他。
- **前端**：按 feature 组织 `pages/ components/ services/ stores/`，每个页面/组件/服务单一职责、自包含。
- **公共层**：跨模块复用只放 `common/`(后端) 与 `utils/`(前端)，避免重复。
- 原则：**高内聚低耦合**，一个改动尽量落在一个目录内，便于后续定位与优化。

### 8.3 代码文档并行（每文件/每函数都有文档，且不漂移）
两层机制，**代码与文档同一次提交**：
- **层 1 代码内（唯一真源，强制）**：每文件顶部 header 注释（职责/输入输出/依赖/对应页面或接口 ID）；每个导出函数/类 TSDoc。
- **层 2 模块级 .md**：每模块一份，记录职责/文件清单/对外接口/依赖/待优化/变更记录。
- **多文件、镜像模块结构**（不写一个大文件——大文件必然腐化、改问题难定位）。

### 8.4 文档位置：新建独立 `开发文档/`（不放 md/）
- `md/` = 产品与架构**设计**（决策级、稳定、全员）；`开发文档/` = 代码级实现（随代码演进、开发维护）。分开避免 md/ 膨胀、职责混淆。
- 规范/索引/模板见 [`开发文档/README.md`](../开发文档/README.md)；`00-代码地图.md` 与各模块文档随对应代码在 Batch 1 起同步创建。
