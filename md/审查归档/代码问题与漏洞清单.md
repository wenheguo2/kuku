> **审计日期**: 2026-07-23  
> **审计范围**: server/ (NestJS后端) + miniapp/ (Taro小程序) + admin/ (Vue管理后台) + md/开发文档  
> **审计方法**: 逐文件代码审查 + 文档对照分析

## 一、高危问题 (High)

### H-01: JWT Secret 硬编码默认值 'dev_secret'

- **文件**: `server/src/modules/auth/jwt.strategy.ts:26`
- **问题**: `secretOrKey: config.get<string>('JWT_SECRET', 'dev_secret')` — 当 `.env` 未设置 `JWT_SECRET` 时，使用弱密钥 `'dev_secret'`。虽然 `environment.validation.ts` 在 production 模式下会校验并阻止启动，但在 development/staging 模式下不检查，攻击者可用此密钥伪造任意用户 JWT。
- **修复建议**: 移除默认值，若未设置 JWT_SECRET 则直接抛出错误阻止启动；或仅在 development 模式下允许默认值，但需确保 staging 环境也走 production 校验。

### H-02: 数据库默认凭据硬编码

- **文件**: `server/src/config/database.config.ts:15-17`
- **问题**: 默认 `DB_USER='kuku_app'`、`DB_PASSWORD='kuku2026'` 硬编码在源码中。若 `.env` 缺失或配置错误，将使用这些凭据连接数据库。密码 `kuku2026` 强度不足，且源码泄露后凭据即暴露。
- **修复建议**: 移除所有默认值，未配置 `DB_PASSWORD` 时拒绝启动。数据库密码应通过环境变量或密钥管理服务注入，不应出现在源码中。

### H-03: 管理员默认密码 'admin123'

- **文件**: `server/src/modules/admin/admin.service.ts:88`
- **问题**: 非生产环境下，`ADMIN_PASSWORD` 默认为 `'admin123'`。虽然 production 模式强制要求 scrypt 哈希，但如果 `NODE_ENV` 未正确设置（如 staging 环境误设为 development），管理员面板将使用弱密码，极易被暴力破解。
- **修复建议**: 移除默认密码，非生产环境也要求设置 `ADMIN_PASSWORD` 或使用 scrypt 哈希。`environment.validation.ts` 中对非 production 但非 development 的环境也应校验。

### H-04: 资源删除时使用 403 而非 404 — 信息泄露

- **文件**: 
  - `server/src/modules/billing/orders.service.ts:134` (`detail` 方法)
  - `server/src/modules/billing/orders.service.ts:140` (`cancel` 方法)
  - `server/src/modules/favorites/favorites.service.ts:56` (`remove` 方法)
  - `server/src/modules/history/history.service.ts:82` (`remove` 方法)
- **问题**: 这些方法先按 `id` 查询资源（不限 userId），再检查 `userId !== 当前用户` 后抛 `403 ForbiddenException`。这与 `ChildOwnershipService` 的安全策略（不存在或不属于均返回 404）不一致。攻击者可通过 403 vs 404 的差异，判断其他用户的资源是否存在（ID 枚举）。
- **修复建议**: 在 `findOne` 的 `where` 中直接加入 `userId` 条件，未找到时统一返回 404。或改为查到后返回 404 而非 403。

### H-05: ValidationPipe 未拒绝未知属性 (forbidNonWhitelisted=false)

- **文件**: `server/src/main.ts:28`
- **问题**: `new ValidationPipe({ transform: true, whitelist: true, forbidNonWhitelisted: false })` — `whitelist: true` 会剥离未装饰的属性，但 `forbidNonWhitelisted: false` 意味着客户端传入额外属性时不会报错，而是静默丢弃。这可能掩盖 bug，且在特定场景下可能被利用进行参数注入（如果 DTO 继承中有未预期的属性）。
- **修复建议**: 在 production 环境设置 `forbidNonWhitelisted: true`，至少在非 GET 请求中拒绝未知属性。

## 二、中危问题 (Medium)

### M-01: 限流仅基于内存 Map，多实例失效

- **文件**: `server/src/common/guards/rate-limit.guard.ts:14`
- **问题**: `private readonly buckets = new Map<string, Bucket>()` — 限流计数器存储在进程内存中。多实例部署时，每个实例独立计数，实际请求量为 `限流阈值 × 实例数`，限流效果大幅降低。代码注释提到"扩为多实例时应把计数迁移到 Redis"，但当前未实现。
- **修复建议**: 多实例部署前必须迁移到 Redis 或网关层限流。单实例阶段应在部署文档中明确标注此限制。

### M-02: 限流基于 request.ip，代理环境下可被伪造

- **文件**: `server/src/common/guards/rate-limit.guard.ts:21`
- **问题**: `const identity = request.user?.userId ? \`u:${request.user.userId}\` : \`ip:${request.ip ?? 'unknown'}\`` — 未认证请求使用 `request.ip` 作为限流标识。若服务部署在 Nginx/CDN 后面且 Express 未设置 `trust proxy`，`request.ip` 可被客户端通过 `X-Forwarded-For` 头伪造，导致限流绕过。
- **修复建议**: 在 `main.ts` 中设置 `app.set('trust proxy', 配置的代理数量)`，或使用 NestJS 的 `ExpressAdapter` 配置 trust proxy。

### M-03: TestStore Redis 连接存在竞态窗口

- **文件**: `server/src/modules/progress/test-store.ts:34-51`
- **问题**: Redis 连接是异步的，`redisReady` 在 `'ready'` 事件回调中设置。从服务启动到 Redis 连接就绪之间，所有挑战答案都存在内存 Map 中。若服务在此窗口内重启，内存中的测试答案丢失，用户提交挑战时会被判为"已过期"。
- **修复建议**: 在 `onModuleInit` 中 `await` Redis 连接完成后再标记服务就绪；或始终使用 Redis（连接失败时抛错而非回退内存）。

### M-04: Admin Token 与用户 JWT 共用同一密钥

- **文件**: `server/src/modules/admin/admin.service.ts:32`
- **问题**: Admin token 通过 `this.jwt.signAsync(...)` 签发，使用与用户 JWT 相同的 `JWT_SECRET`。虽然 `JwtStrategy.validate` 会拒绝带 `role` 字段的 token（jwt.strategy.ts:32），且 `AdminAuthGuard` 独立校验 `role === 'admin'`，但一旦 `JWT_SECRET` 泄露，攻击者可同时伪造用户和管理员 token。
- **修复建议**: 使用独立的 `ADMIN_JWT_SECRET` 环境变量为管理员 token 签发和验证使用不同密钥，实现密钥隔离。

### M-05: Admin Token 存储在 localStorage — XSS 可窃取

- **文件**: 
  - `admin/src/api/index.ts:12` — `localStorage.getItem('admin_token')`
  - `admin/src/views/Login.vue:42` — `localStorage.setItem('admin_token', result.access_token)`
- **问题**: 管理后台 token 存储在 `localStorage` 中，可被 XSS 攻击窃取。管理后台引入了 Element Plus 等第三方库，若存在 XSS 漏洞，攻击者可直接获取管理员 token。
- **修复建议**: 理想方案是使用 httpOnly cookie 存储 token；若必须用 localStorage，应加强 CSP 策略并定期审计第三方依赖的 XSS 漏洞。

### M-06: 管理员密码验证的时序泄露

- **文件**: `server/src/modules/admin/admin.service.ts:89-91`
- **问题**: 开发模式下，当 `expected.length !== actual.length` 时直接返回 `false`，不执行 `timingSafeEqual`。这泄露了密码长度信息（通过响应时间差异），攻击者可据此缩小暴力破解范围。
- **修复建议**: 对不同长度也执行 `timingSafeEqual`（先填充到相同长度），或统一使用 scrypt 验证（包括开发模式）。

### M-07: 埋点 properties 无大小限制 — 潜在 DoS

- **文件**: `server/src/modules/track/track.controller.ts:17`
- **问题**: `@IsOptional() @IsObject() properties?: Record<string, unknown>` — 无大小限制。攻击者可发送包含超大 JSON 对象（如数 MB）的埋点请求，存入数据库的 JSONB 字段，造成存储膨胀和查询性能下降。限流规则对 `/track` 走 "other" 100/分钟，允许大量大对象注入。
- **修复建议**: 对 `properties` 的 JSON 序列化长度设置上限（如 4KB），超限拒绝。可自定义 `@MaxJSONSize()` 装饰器或在 pipe 中校验。

### M-08: 孩子档案数量无上限

- **文件**: `server/src/modules/children/children.controller.ts:33`
- **问题**: `create` 方法直接创建档案，未检查当前用户已有档案数量。攻击者可无限创建孩子档案，造成数据库膨胀。API 文档 (md/11 §6.4) 未明确限制，但 PRD 中 MVP 设计为单孩子/少数孩子场景。
- **修复建议**: 添加档案数量上限（如 5 个），超过时返回 400。

### M-09: 会员过期状态不更新数据库

- **文件**: 
  - `server/src/modules/membership-access/membership-access.service.ts:15-22` — `isActive()` 读时判断 `endDate >= today`，但不更新 `status` 字段
  - `server/src/modules/billing/billing.controller.ts:30` — 同样读时判断过期
- **问题**: 会员 `status` 字段始终为 `'active'`（除非手动取消），即使已过期。这导致：
  1. `MembershipController.status()` 返回 `expired` 但数据库仍为 `active`，数据不一致
  2. 查询 `status: 'active'` 的查询会包含已过期会员，影响管理后台统计准确性
  3. 依赖 `status` 字段的逻辑（如未来增加自动续费）可能行为异常
- **修复建议**: 增加定时任务或读时更新机制，将过期会员的 `status` 更新为 `'expired'`；或在所有查询中同时检查 `status = 'active' AND end_date >= now()`。

### M-10: 微信 API Secret 通过 URL 查询参数传递

- **文件**: `server/src/modules/wechat.service.ts:54`
- **问题**: `const url = \`https://api.weixin.qq.com/sns/jscode2session?appid=${appid}&secret=${secret}&...\`` — WX Secret 作为 URL 查询参数传递。虽然这是微信官方 API 要求的方式，但 URL 中的 secret 可能被：
  1. 服务器访问日志记录
  2. 代理服务器缓存
  3. 网络中间设备截获
- **修复建议**: 这是微信 API 的限制，难以完全避免。建议：
  1. 确保服务器访问日志不记录完整 URL（对含 secret 的请求脱敏）
  2. 使用 HTTPS 连接微信 API（已默认使用）
  3. 在日志中对 `secret` 参数做掩码处理

### M-11: CORS 开发环境允许所有来源

- **文件**: `server/src/main.ts:50-52`
- **问题**: `origin: isProduction ? corsOrigins : true` — 非生产环境下 `origin: true` 允许任意来源跨域请求，且 `credentials: true` 允许携带凭据。若开发/测试环境暴露在公网，可被 CSRF 攻击。
- **修复建议**: 开发环境也限制为 `localhost` 系列地址，或通过 `.env` 的 `CORS_ORIGINS` 配置。

## 三、低危问题 (Low)

### L-01: 小程序 Token 明文存储

- **文件**: `miniapp/src/services/storage.ts:37-40`
- **问题**: JWT token 通过 `Taro.setStorageSync` 明文存储。微信小程序的 Storage 不提供加密，设备越狱后 token 可被提取。
- **影响**: 小程序环境的通用限制，低风险。退出登录时已正确清除 token。

### L-02: Mock 数据包含在生产构建中

- **文件**: `miniapp/src/services/mock.ts`
- **问题**: mock 数据文件始终被打包进小程序 bundle，即使 `USE_MOCK=false` 时不会使用。增加了包体积（微信小程序有 2MB 主包限制）。
- **修复建议**: 使用 Taro 的环境条件编译，在生产构建时排除 mock 文件。

### L-03: 音频播放器无错误恢复机制

- **文件**: `miniapp/src/services/audioPlayer.ts:46`
- **问题**: `ctx.onError((e) => Taro.showToast({ title: \`播放失败: ${e.errMsg ?? ''}\`, icon: 'none' }))` — 播放失败仅弹 toast，无自动重试或降级策略。儿童使用场景下网络不稳定时体验差。
- **修复建议**: 增加有限次自动重试（如 3 次），重试失败后提示用户检查网络。

### L-04: 无 HTTPS 强制重定向

- **文件**: `server/src/main.ts:55-56`
- **问题**: 服务直接监听 HTTP 端口，无 HTTPS 重定向。生产环境需依赖 Nginx/网关层做 TLS 终结和 HTTP→HTTPS 重定向。若网关配置遗漏，API 将以明文传输 JWT。
- **修复建议**: 在部署文档中强制要求 Nginx 配置 HTTP 301 到 HTTPS；或添加 NestJS 中间件检测 `x-forwarded-proto` 并重定向。

### L-05: 管理后台无 Content Security Policy

- **文件**: `admin/vite.config.ts`
- **问题**: Vite 配置中未设置 CSP 相关响应头。管理后台作为高权限面板，缺少 CSP 防护增加了 XSS 攻击的可行面。
- **修复建议**: 在生产部署的 Nginx 配置中添加 CSP 头，或在 Vite 构建中通过插件注入。

### L-06: 静态文件根路径未做安全校验

- **文件**: `server/src/app.module.ts:46`
- **问题**: `rootPath: join(process.cwd(), config.get<string>('STATIC_ROOT', '../production'))` — `STATIC_ROOT` 来自环境变量，若被设置为恶意路径（如 `/etc`），可导致任意文件读取。
- **修复建议**: 对 `STATIC_ROOT` 做路径校验（必须在项目目录下），或使用白名单目录。

### L-07: 家长设置 JSON 合并无字段校验

- **文件**: `server/src/modules/parent/parent.service.ts:32`
- **问题**: `s.settingsJson = { ...(s.settingsJson ?? {}), ...settingsJson }` — 客户端可覆盖 settings JSON 中的任意 key，无字段白名单。虽然当前 settings JSON 仅用于展示配置，但若未来扩展存储敏感配置，可能产生安全问题。
- **修复建议**: 定义 settings JSON 的允许字段列表，在合并时只接受白名单内的 key。

### L-08: 协议版本仍为 draft 状态

- **文件**: `miniapp/src/config/agreements.ts:6-8`
- **问题**: 三个协议版本均为 `'2026-07-draft'`。虽然 `config/index.ts` 的 release 门禁和 `environment.validation.ts` 的 production 校验都会阻止 draft 版本上线，但当前开发阶段所有用户登录时同意的都是草案版本，上线前需同步更新。
- **修复建议**: 上线前将协议版本更新为法务定稿版本，并确保前后端、`.env` 三处一致。

### L-09: 订单号生成存在碰撞风险

- **文件**: `server/src/modules/billing/orders.service.ts:48`
- **问题**: `const orderNo = \`ORD${Date.now()}${Math.floor(Math.random() * 1000)}\`` — 订单号基于时间戳 + 0-999 随机数。同一毫秒内并发请求有 1/1000 碰撞概率，且 `order_no` 有唯一约束，碰撞时会抛数据库异常。
- **修复建议**: 使用 UUID 或雪花算法生成订单号；或增加随机数范围/加入 userId 作为种子。

### L-10: 全局异常过滤器可能泄露内部异常信息

- **文件**: `server/src/common/filters/all-exceptions.filter.ts:27`
- **问题**: 对 `HttpException` 的响应，将 `exception.getResponse()` 中的 `message` 直接返回给客户端。若 NestJS 内部的 class-validator 或 DTO 验证消息中包含字段名/内部结构信息，会泄露给客户端。虽然比直接返回 `exception.message` 安全，但仍可能暴露 DTO 结构。
- **修复建议**: 对非生产环境保留详细消息便于调试；生产环境对 500 错误返回通用消息，对 400 类错误做字段名脱敏。

## 四、文档与代码不一致

### D-01: API 文档搜索接口描述与实现不一致

- **文件**: `md/11-API接口文档.md §8` (第 772-800 行)
- **问题**: API 文档 §8.1 标题为"MVP 搜索实现（客户端本地索引）"，说明"当前不提供 `/api/v1/search`"，搜索由小程序本地完成。但文档中仍给出了完整的 `data` 响应结构和字段说明，格式与服务端 API 一致，容易误导开发者认为存在服务端搜索接口。
- **建议**: 明确标注此为客户端本地匹配的数据结构示例，而非服务端 API 契约。

### D-02: API 文档中订单详情缺少错误码说明

- **文件**: `md/11-API接口文档.md §7.2` (第 742-768 行)
- **问题**: 文档描述了 `GET /api/v1/orders/{id}` 返回订单详情，但未说明当 `id` 不属于当前用户时返回 403（代码实现）还是 404（与 ChildOwnershipService 一致的安全策略）。代码中 `orders.service.ts:134` 返回 `ForbiddenException('无权查看该订单')`，但 API 文档未记录此行为。
- **建议**: 在 API 文档中补充 403 场景说明，或修改代码统一返回 404 以与安全策略一致。

### D-03: 管理后台 AdminAuthGuard 在 @Public 类上 — 守卫顺序未文档化

- **文件**: `server/src/modules/admin/admin.controller.ts:16`
- **问题**: `AdminController` 类标记了 `@Public()`，使全局 `JwtAuthGuard` 跳过所有 admin 路由。`stats` 方法通过 `@UseGuards(AdminAuthGuard)` 独立鉴权。这种设计意味着：
  1. 全局守卫顺序: JwtAuthGuard(跳过) → RateLimitGuard(IP级限流) → VipGuard(跳过) → AdminAuthGuard(验证admin token)
  2. 限流基于 IP 而非 admin 身份（因 request.user 未设置）
  3. 此守卫交互逻辑未在开发文档中记录
- **建议**: 在开发文档中记录 admin 路由的守卫执行顺序；考虑将 admin login 和 admin API 分离到不同 controller，login 保持 @Public，stats 不标 @Public 但自定义全局守卫逻辑。

## 五、架构与设计建议

### A-01: 缺少请求体大小限制

- **文件**: `server/src/main.ts`
- **问题**: 未配置 `express.json()` 的 `limit` 选项，默认允许较大的请求体。配合 M-07（埋点 properties 无大小限制），可被用于 DoS。
- **建议**: 在 bootstrap 中设置 `app.use(express.json({ limit: '1mb' }))` 或使用 NestJS 的 `bodyParser` 配置。

### A-02: 缺少 Helmet 等安全中间件

- **文件**: `server/src/main.ts:33-43`
- **问题**: 手动设置了部分安全头（X-Content-Type-Options, X-Frame-Options 等），但缺少 `Strict-Transport-Security (HSTS)`、`Content-Security-Policy` 等重要头。注释中提到"helmet 等价的轻量子集"，但实际覆盖不完整。
- **建议**: 直接使用 `helmet` 中间件（npm 包），提供更完整的安全头覆盖。

### A-03: 缺少 API 请求日志与审计日志

- **问题**: 全局异常过滤器记录了 error 级别日志，但无请求级别日志（请求路径、方法、耗时、状态码）。管理后台的操作（如 stats 查询）无审计日志。
- **建议**: 添加 NestJS 的 `Logger` 中间件记录所有 API 请求；对 admin 操作添加专门的审计日志表。

### A-04: 缺少依赖安全扫描

- **文件**: `server/package.json`
- **问题**: 项目依赖列表中未配置安全扫描。`passport@0.7.0` 等库可能存在已知 CVE 漏洞。
- **建议**: 在 CI/CD 中集成 `npm audit` 或 Snyk 等依赖安全扫描工具。
