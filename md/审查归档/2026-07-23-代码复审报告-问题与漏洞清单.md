## 3. 高严重问题（H）

### H-01 生产环境 JWT 默认密钥弱 / 可预测
- **文件**: `server/src/modules/auth/auth.module.ts:25`
- **状态**: 旧问题，**仍存在**
- **代码**：
  ```ts
  secret: configService.get('JWT_SECRET') || 'dev_secret',
  ```
- **问题**：未配置 `JWT_SECRET` 时回退到固定字符串 `dev_secret`，可直接伪造 token，导致水平越权、管理员身份伪造等。
- **建议**：`JWT_SECRET` 必须强制从环境变量读取，无默认值；且生产环境通过 `environment.validation.ts` 校验长度 ≥ 32。

### H-02 数据库默认凭据硬编码
- **文件**: `server/src/config/database.config.ts:7`
- **状态**: 旧问题，**仍存在**
- **代码**：
  ```ts
  password: configService.get('DB_PASSWORD') || 'kuku2026',
  ```
- **问题**：若环境变量未配置则使用公开密码，易被爆破/内网横向。
- **建议**：删除默认值，无 `DB_PASSWORD` 时启动失败；`environment.validation.ts` 增加对 DB 密码复杂度校验。

### H-03 管理后台默认账号密码与无登录保护
- **文件**: `server/src/modules/admin/admin.service.ts:24`
- **状态**: 旧问题，**仍存在**
- **代码**：
  ```ts
  if (username === 'admin' && hash === this.hash('admin123')) {
  ```
- **问题**：默认密码 admin123；无账号锁定、无失败次数限制、无密码修改强制流程。
- **建议**：
  1. 初始密码必须在首次启动时由随机环境变量或初始化命令生成并写入日志。
  2. 增加失败 5 次锁定 15 分钟的机制（Redis/内存）。
  3. 生产环境强制 `AdminLoginDto.password` 至少 12 位且包含大小写+数字。

### H-04 Admin token 与小程序用户 JWT 共用同一密钥
- **文件**: `server/src/modules/auth/auth.module.ts:25` + `server/src/modules/admin/admin-auth.guard.ts:12`
- **状态**: 旧问题，**仍存在**
- **问题**：两套 token 使用同一 `JWT_SECRET`。一旦用户侧密钥泄露，可伪造 admin token（虽然当前用户 token 不含 `role: admin`，但共享密钥不符合权限隔离原则）。
- **建议**：引入 `ADMIN_JWT_SECRET`，admin 模块使用独立密钥签发/验证。

### H-05 脚本硬编码 TTS API 密钥
- **文件**: `config/tts_providers.json:13`
- **状态**: **新发现**
- **代码**：
  ```json
  "key": "mimo_..."
  ```
- **问题**：真实的 TTS 服务密钥直接提交到仓库，任何人可调用该服务，造成费用与滥用风险。
- **建议**：
  1. 立即在服务商控制台撤销并重置该 key。
  2. 改为从环境变量或 `.env` 读取；配置模板中只保留空占位符或 `env://TTS_KEY` 引用。
  3. 使用 git 历史清理工具（如 `git filter-repo`）将该密钥从提交记录中移除。

### H-06 脚本硬编码 SSH 登录凭据
- **文件**: `脚本/common.py:19-21`
- **状态**: **新发现**
- **代码**：
  ```python
  REMOTE_HOST = "192.168.1.101"
  REMOTE_USER = "root"
  REMOTE_PASS = "123456"
  ```
- **问题**：服务器 root 密码、IP、用户名全部硬编码在仓库，可被直接登录。
- **建议**：
  1. 立即修改该服务器 root 密码；禁用密码登录，改用 SSH Key。
  2. 凭据迁移到环境变量 / CI secret；脚本通过 `paramiko` 读取 `SSH_PRIVATE_KEY`。
  3. 仓库中保留 `REMOTE_HOST` 等可通过 `.env` 覆盖即可，不要写密码。

### H-07 脚本硬编码用户 JWT / MiniMax 会话凭证
- **文件**: `脚本/batch_songs.py:13-21`
- **状态**: **新发现**
- **代码**：
  ```python
  TOKEN = "eyJhbGciOiJIUzI1NiIs..."
  APP_ID = "..."
  OP_TICKET = "..."
  DEVICE_ID = "..."
  UUID = "..."
  ```
- **问题**：即使 token 已过期，会话指纹、设备 ID、app_id 等仍属于用户/平台敏感信息，且一旦 token 未过期即可被冒用。
- **建议**：从环境变量读取；如脚本仅用于一次性测试，删除或放入 `.gitignore` 的本地配置文件中。

### H-22 删除孩子无“至少保留一个”保护
- **文件**: `server/src/modules/children/children.controller.ts:45`
- **状态**: 旧问题，**仍存在**
- **代码**：
  ```ts
  @Delete(':id')
  async remove(@Param('id') id: string, @UserId() userId: string) {
    return this.children.remove(+id, userId);
  }
  ```
- **问题**：可删除用户下最后一个孩子，导致账号无孩子可用、学习进度空挂、家长控制数据异常。
- **建议**：在 `children.service.remove` 中查询 `COUNT(*)`，删除后至少保留 1 个孩子；否则返回 400。

### H-29 开发环境 mock 登录共享同一测试用户
- **文件**: `server/src/modules/auth/wechat.service.ts:14` + `server/src/modules/auth/auth.service.ts:51`
- **状态**: 旧问题，**仍存在（开发环境）**
- **代码**：
  ```ts
  return { openid: 'default_test_user' } as any;
  ```
- **问题**：所有未传 code 的测试请求都映射到同一 openid，数据互相污染；若误发布到生产可被利用。
- **建议**：mock 必须显式开启且仅绑定 `NODE_ENV=development`；每次 mock 生成随机 openid，并增加 `X-Mock-User` 请求头白名单。

### M-06 全局 `ValidationPipe` 未开启 `forbidNonWhitelisted`

- **代码**：
  ```ts

  ```
- **问题**：客户端可提交额外字段并被静默忽略，可能导致 mass assignment 或业务字段误用。
- **建议**：改为 `true`；同时给所有 DTO 加上 `class-validator` 装饰器。

### M-10 埋点 event 名称无白名单

- **状态**: 旧问题，**部分修复**
- **代码**：仅限制 `properties` 大小 4096；未限制 `event` 取值。
- **问题**：攻击者可写入任意 event 名称，污染埋点数据或存储恶意长字符串。
- **建议**：定义允许事件白名单（如 `event.enum.ts`），并在 controller 中校验；同时限制 `event` 长度 ≤ 64。

### M-11 家长设置任意 JSON 合并，无 schema 校验
- **文件**: `server/src/modules/parent/parent.service.ts:48`
- **状态**: 旧问题，**仍存在**
- **代码**：
  ```ts
  const next = { ...current, ...dto.settings };
  ```
- **问题**：客户端可注入任意字段（如修改角色、覆盖内部标志）。
- **建议**：使用 `Joi` / `zod` 定义 `SettingsSchema` 并做严格合并，或定义独立字段 DTO。

### M-12 后端输入校验大面积缺失
- **文件**: 贯穿 `server/src/modules/**/*.controller.ts`
- **状态**: 旧问题，**扩大/仍存在**
- **问题**：除 `AdminLoginDto`、`UserUpdateDto`、`DeleteAccountDto` 等少量 DTO 外，多数 `@Body()` 参数为无装饰器的 class/interface，导致 `ValidationPipe` 无法校验。例如：
  - `progress/test.controller.ts` 的 `submitQuiz` 直接接收对象数组，无长度、字段类型校验。
  - `parent.controller.ts` 的 `updateSettings` 接收 `UpdateSettingsDto` 但只声明字段，无装饰器。
- **建议**：
  1. 统一为所有接口输入定义 DTO class，并添加 `class-validator` 装饰器（`@IsString`、`@MaxLength`、`@IsArray` 等）。
  2. 在 `main.ts` 启用 `forbidNonWhitelisted: true` + `whitelist: true`。
  3. 对 `track` 的 `properties` 做 JSON Schema 校验。

### M-13 开发环境 CORS 允许任意来源 + 凭证
- **文件**: `server/src/main.ts:19`

### M-18 普通挑战 `test_id` 可预测

### M-19 普通挑战重试限制实际失效（无限重试）
- **文件**: `server/src/modules/progress/progress.service.ts:95` + `:133`
- **状态**: 旧问题，**形式变化后仍存在**
- **代码**：
  ```ts
  // getQuiz 每次出题都会把 retryUsed 置 0
  await repo.update({ id: row.id }, { retryUsed: 0 });
  // submitQuiz 仅在失败时 +1
  const canRetry = !passed && row.retryUsed < 1;
  ```
- **问题**：用户失败一次后，只要重新调用 `getQuiz` 生成新试卷，`retryUsed` 即被重置，等于可无限重试；与 PRD “仅 1 次重试” 不符。
- **建议**：将 `retryUsed` 生命周期绑定到当前题目组，而不是每次出题重置；或在 `getQuiz` 中根据上一次未通过记录继承 `retryUsed`。

### M-20 综合挑战每字仅 1 题 / 仅校验长度
- **文件**: `server/src/modules/progress/progress.service.ts:272-290`
- **状态**: 旧问题，**仍存在**
- **问题**：`submitComprehensive` 只校验 `answers.length !== 10`，每字 1 题与 PRD 不符；判题逻辑依赖客户端答案顺序。
- **建议**：按 PRD 每字生成 3 类题型；服务端记录题目顺序并校验答案对应关系。

### M-23 `events.child_id` 外键未声明 `ON DELETE`
- **文件**: `server/src/entities/event.entity.ts:21`
- **状态**: 旧问题，**仍存在**

- **问题**：删除孩子时，若未执行 `deleteAccount` 中的手动清理，事件表可能因外键约束报错或留下孤儿事件。
- **建议**：`@ManyToOne(() => ChildProfile, { onDelete: 'SET NULL' })`；并在删除孩子 service 中统一处理。

### M-24 监护人同意无撤回接口

### M-26 限流使用内存 Map 且 IP 获取依赖配置
- **文件**: `server/src/common/guards/rate-limit.guard.ts:15` + `server/src/main.ts:11`

- **问题**：集群多实例时内存 Map 无法共享；`request.ip` 在反向代理后可能为代理 IP，需 `trust proxy` 配合环境变量。
- **建议**：生产环境使用 Redis 限流（如 `@nestjs/throttler` + Redis store）；默认开启 `trust proxy` 并从 `X-Forwarded-For` 获取真实 IP。

### M-28 删除账号后可能残留学习进度数据
- **文件**: `server/src/entities/learning-progress.entity.ts` + `server/src/modules/auth/auth.service.ts`（deleteAccount）
- **状态**: **新发现**
- **问题**：`learning_progress` 表没有显式外键关联 `child_profiles`，`deleteAccount` 只删除 `child_profiles`，未删除对应学习进度。GDPR/未成年人合规场景下属于数据残留。
- **建议**：在 `deleteAccount` 事务中根据 `child_id` 删除 `learning_progress`、`favorites`、`history` 等所有子表；或建立 `ON DELETE CASCADE` 外键。

### M-29 后台统计接口 `@Public()` 与 Guard 冗余混用
