# 酷酷儿童故事 — 代码审查报告（问题与漏洞清单）

> 审查范围：`server/`（NestJS 后端）、`miniapp/`（Taro 小程序）、`admin/`（Vue3 后台）、`server/src/db/schema.sql`（数据库基线）及相关配置文件。
> 审查维度：安全漏洞、权限控制、业务逻辑缺陷、并发竞态、性能隐患、代码质量。
> 审查日期：2026-07-23

---

## 一、总体评价

代码整体质量较高，已具备以下良好的安全基线（值得肯定）：

- ✅ 全局 JWT 守卫默认需登录，`@Public()` 白名单放行机制清晰
- ✅ 所有 `child_id` 入口统一经 `ChildOwnershipService.assertOwner` 归属校验，且不存在/非本人统一返回 404（不泄露档案存在性）
- ✅ 挑战答案不下发前端、服务端判分（综合/普通挑战），`toPublic()` 剥离 `correct_option`
- ✅ 生产环境启动门禁 `environment.validation.ts`：强制真实凭据、禁 mock/stub、禁弱 JWT 密钥、禁 draft 协议
- ✅ 全局异常过滤器对非 HTTP 异常只回"服务器繁忙"，内部堆栈仅进服务端日志，不泄漏 SQL/路径/凭据
- ✅ 全部 SQL 使用参数化查询（`$1` 占位 / QueryBuilder 参数），无注入风险
- ✅ `markPaid` 使用悲观行锁（订单行 + 用户行）防并发重复开通会员
- ✅ `.env` 已加入 `.gitignore`，凭据不入库；`.env.example` 脱敏
- ✅ 统一响应包络 `{code,message,data}`、全局 ValidationPipe（whitelist）

但仍存在以下需修复的问题，按严重程度分级。

## 二、高危问题（High）

### H-1 复习接口允许客户端自报成绩（作弊漏洞）⭐

**位置**：`server/src/modules/progress/progress.controller.ts` L50-54；`progress.service.ts` L327-340

**问题**：`POST /api/v1/progress/review/refresh` 的 `passed` 字段由客户端直接传入，服务端不做任何判分校验：

```ts
class ReviewRefreshDto {
  @IsString() child_id: string;
  @IsString() word_id: string;
  @IsBoolean() passed: boolean;   // ← 客户端自报
}
```

`reviewRefresh()` 无条件信任 `passed`：传 `true` 即刷新 `review_due_at`、保持"好伙伴(3)"；传 `false` 才回落。

**危害**：与文件头部声明的"★ 判分全在服务端"原则直接矛盾。客户端（或被篡改的请求）可永远上报 `passed: true`，使所有字永久停留在"好伙伴"等级，完全绕过间隔复习机制，成长体系数据失真。普通挑战/综合挑战均已服务端判分，唯独复习环节是客户端自报，属设计缺口。

**建议**：复习也应走"服务端出题 → 客户端作答 → 服务端判分"流程（可复用 `TestStore` + `generateNormalQuiz`），或至少引入答题正确率阈值，不得直接信任 `passed`。

### H-2 管理员默认弱口令 + 无账号锁定（爆破风险）

**位置**：`server/src/modules/admin/admin.service.ts` L83-91；`admin.controller.ts`

**问题**：
1. 开发模式下管理员密码回退为明文 `admin123`（`ADMIN_PASSWORD` 默认值），且通过 `ADMIN_PASSWORD` 环境变量以明文存储/比对。
2. 管理员登录**无账号级锁定、无验证码、无失败次数累计**。仅靠全局 `RateLimitGuard` 的 `/auth/login` 规则限制 20 次/分钟/身份。

**危害**：若开发/测试服务经内网穿透或误暴露公网，攻击者可以 20 次/分钟的速率持续爆破 `admin/admin123` 类弱口令，且永不锁定。管理端掌握全库统计数据，一旦失守影响较大。

**建议**：
- 生产已强制 `ADMIN_PASSWORD_SCRYPT`（已做，保持）；开发环境也应避免在代码中硬编码 `admin123` 默认值，改为未配置即拒绝或显著告警。
- 增加账号级失败计数与临时锁定（如 5 次失败锁 15 分钟），或接入验证码。

---

### H-3 AdminController 类级 `@Public()` 的裸露风险

**位置**：`server/src/modules/admin/admin.controller.ts` L16-18

**问题**：`@Public()` 加在**类**上，使该控制器所有路由默认绕过全局 JWT 守卫：

```ts
@Public()
@Controller('admin')
export class AdminController {
```

当前 `stats` 靠方法级 `@UseGuards(AdminAuthGuard)` 保护、`login` 本就应公开，勉强成立。但这是"默认危险"的写法——后续任何人新增管理路由时，只要忘记加 `@UseGuards(AdminAuthGuard)`，该接口就会**完全无鉴权裸露**（全局 JWT 守卫已被类级 @Public 关闭）。

**建议**：移除类级 `@Public()`，仅在 `login` 方法上标注 `@Public()`；或为 admin 控制器统一注册 `AdminAuthGuard` 为控制器级守卫，login 单独豁免。

## 三、中危问题（Medium）

### M-1 JWT 密钥存在弱默认值回退

**位置**：`server/src/modules/auth/jwt.strategy.ts` L26；`auth.module.ts` L28

**问题**：两处均写 `config.get<string>('JWT_SECRET', 'dev_secret')`。若 `.env` 缺失该项，开发环境将使用 `dev_secret` 这一公开可知的弱密钥，可伪造任意用户的合法 JWT（payload 仅需数字 `sub` + 对应 `openid`）。虽然生产门禁会拦截弱密钥，但开发/测试环境若暴露同样可被利用。

**建议**：去掉代码内 `'dev_secret'` 回退，改为"未配置即启动失败"，或在环境校验中对所有环境强制 JWT_SECRET 非空。

### M-2 订单号可预测/可枚举

**位置**：`server/src/modules/billing/orders.service.ts` L48

```ts
const orderNo = `ORD${Date.now()}${Math.floor(Math.random() * 1000)}`;
```

**问题**：订单号 = 毫秒时间戳 + 0~999 随机数，熵极低。知道大致下单时间即可在 1000 种内枚举出订单号。订单号是支付/对账业务凭证，真实微信支付接入后会暴露在对账、回调等环节。

**建议**：使用 `crypto.randomBytes`/`randomUUID` 生成高熵订单号（如 `ORD + 时间戳 + 8~16 位加密随机`）。

### M-3 用户手机号未脱敏返回（儿童应用合规）

**位置**：`server/src/modules/auth/user.controller.ts` L45

**问题**：`GET /user/profile` 直接返回 `phone: user.phone`。本项目面向儿童，受《个人信息保护法》《未成年人网络保护条例》约束，手机号属敏感个人信息，不应在资料接口明文返回。

**建议**：返回时脱敏（如 `138****1234`），或前端无展示需求则直接不返回。

### M-4 埋点 `properties` 字段无大小限制（存储型 DoS）

**位置**：`server/src/modules/track/track.controller.ts` L17

**问题**：`properties` 仅 `@IsObject()` 校验，无体积/深度/键数限制。恶意用户可反复提交 MB 级 JSON，快速撑爆 `events.properties`（JSONB）存储与带宽。

**建议**：限制序列化后体积（如 ≤ 4KB）与嵌套深度，超限拒绝。

### M-5 家长设置 `settings` 无内容校验

**位置**：`server/src/modules/parent/parent.controller.ts` L19；`parent.service.ts` L28-34

**问题**：`settings` 为任意 `@IsObject()`，`updateSettings` 直接 `{ ...old, ...new }` 合并进 `settings_json`。可写入任意键、超大值，长期累积污染配置字段。

**建议**：定义允许的键白名单（theme / review_interval_days 等）与取值范围，DTO 层严格校验。

### M-6 多个字符串字段缺少 MaxLength（应层校验缺失）

**位置**：`history.controller.ts`（content_id/content_title/subject_id）、`favorites.controller.ts`（content_id/content_title/subject_id）、`track.controller.ts`（event）

**问题**：上述字段仅 `@IsString()`，无长度上限。虽然 DB 层 VARCHAR(256/64) 会因超长报 500，但应在 DTO 层用 `@MaxLength()` 提前拦截为 400，避免把 DB 错误暴露为 500、也避免日志被超长串污染。

**建议**：按 DB 列长度补充对应 `@MaxLength()`。

### M-7 开发环境 CORS 全开 + 携带凭据

**位置**：`server/src/main.ts` L49-53

```ts
app.enableCors({ origin: isProduction ? corsOrigins : true, credentials: true });
```

**问题**：非生产环境 `origin: true`（反射任意来源）且 `credentials: true`。开发服务若经内网穿透暴露，任意站点可跨域携带用户凭据发起请求。

**建议**：开发环境也收敛为明确的本地来源白名单（localhost:5173、微信开发者工具等），不要 `true`。

## 四、低危 / 代码质量问题（Low）

### L-1 `getOrCreate` 先查后建并发竞态

**位置**：`progress.service.ts` L42-49。先 `findOne` 再 `create+save`，并发下两个请求可能同时判定"不存在"并重复插入，触发 `UNIQUE(child_id, word_id)` 约束报 500。建议改 `upsert`（TypeORM `upsert()` 或 `ON CONFLICT DO UPDATE`）。

### L-2 收藏上限校验 TOCTOU 竞态

**位置**：`favorites.service.ts` L31-50。先 `count` 判断是否满 500 再 `save`，并发下可突破上限。建议在唯一键 + 事务内校验，或接受少量超限后用 DB 约束兜底。

### L-3 多处全量加载进度记录进内存（性能隐患）

**位置**：
- `progress.service.ts` `summary()` L369-388：`find({ where: { childId } })` 拉全部字进度后内存 filter 统计
- `achievements.service.ts` `getCollection()` L29-43、`grantEligibleStickers()` L63-85：同样全量加载

**问题**：随着学习量增长（数千字 × 多学科），每次总览/收集册/发贴纸都把全表行载入内存聚合，O(N) 内存与 IO。应改为 SQL 聚合（`GROUP BY subject, current_stage` / `COUNT ... WHERE current_stage=3`）。

### L-4 成就发放 N+1 查询

**位置**：`achievements.service.ts` L63-85。每学科每里程碑一次 `findOne`（3 学科 × 3 里程碑 = 最多 9 次查询）。建议一次性查出该 child 已有成就后内存比对。

### L-5 题目确定性生成 + 提交后回显正确答案（挑战形同虚设）

**位置**：`quiz.util.ts`（干扰项池固定、正确答案由 wordText 确定性派生）；`progress.service.ts` L133（提交结果回显每题 `correct_option`）。

**问题**：同一字的题目内容完全确定（仅选项顺序随机），且首次提交后响应即告知每题正确选项。用户重新取题（内容相同）后必然全对，普通挑战可被"背答案"刷过。虽已注明"真实题库接入后替换"，但当前阶段挑战判定无实际区分度。

**建议**：接入真实题库前，至少做到提交后不回显 `correct_option`（仅回显对错），并扩大/随机化干扰项池。

### L-6 普通挑战 test_id 可预测

**位置**：`progress.service.ts` L93：`t_${wordId}_${Date.now()}`。综合挑战已用随机后缀（L161/L193），普通挑战建议统一为加密随机，降低 test_id 被猜测的风险面。

### L-7 `orders.create` 冗余条件判断

**位置**：`orders.service.ts` L40-46。L40 `if (!this.isStub()) throw` 已保证后续 `isStub()` 恒真，L44 的 `this.isStub() &&` 为冗余条件，可简化为 `if (!this.allowStub())`。

### L-8 删除孩子无"至少保留一个"保护

**位置**：`children.controller.ts` L45-54。允许删除名下所有孩子（含登录自动建的默认档案），破坏"至少存在一个默认 child_profile"的不变量（见 `auth.service.ts` L86-91 的注释约束），可能导致后续成长数据无处落库、前端 selectedChildId 失效。建议禁止删除最后一个档案，或删除后自动重建默认档案。

### L-9 `users.updated_at` 无数据库触发器

**位置**：`schema.sql` L17。`updated_at` 仅 `DEFAULT CURRENT_TIMESTAMP`，无 `ON UPDATE` 触发器，完全依赖 TypeORM `@UpdateDateColumn` 在应用层维护；任何绕过 ORM 的原生 SQL 更新都不会刷新该字段。建议补 `BEFORE UPDATE` 触发器。

### L-10 `events.child_id` 外键缺失联策略（schema 与代码不一致）

**位置**：`schema.sql` L151（`child_id BIGINT REFERENCES child_profiles(id)`，无 ON DELETE）；`children.controller.ts` L48-52 删除孩子前手动 `UPDATE events SET child_id=NULL`。

**问题**：schema 未定义 `ON DELETE SET NULL`，靠业务代码手动置 NULL 兜底，属脆弱设计（代码注释也承认"外键尚未升级为 ON DELETE SET NULL"）。任何新增删除孩子的路径若忘记这一步都会 FK 违约报错。建议将外键升级为 `ON DELETE SET NULL` 并移除手工补丁。

### L-11 监护人同意缺少"撤回"接口

**位置**：`consent-record.entity.ts`（有 `withdrawn_at` 字段）；无对应 endpoint。儿童隐私合规（PIPL / 《儿童个人信息网络保护规定》）要求监护人可撤回同意，当前仅能"同意"不能"撤回"，字段形同虚设。建议补撤回接口并联动账号处理。

### L-12 admin token 存 localStorage（XSS 风险面）

**位置**：`admin/src/api/index.ts` L12；`admin/src/views/Login.vue` L42。管理端 token 存 `localStorage`，若后台存在 XSS 即可被窃取。后台攻击面虽小，但管理 token 权限高。建议改 httpOnly Cookie 或至少配合 CSP。

### L-13 微信登录 `code` 在 DTO 层为可选

**位置**：`login.dto.ts` L8-10（`code` 为 `@IsOptional()`）。real 模式下由 `wechat.service.ts` L51-53 兜底校验缺失 code，但 DTO 层未强制。建议 real 模式在控制器/服务入口显式断言 code 必填，避免依赖隐式分支。

### L-14 限流桶清理策略偏宽松

**位置**：`rate-limit.guard.ts` L47-52。仅当桶数量 ≥ 10000 才清理过期桶；高并发不同 IP 场景下 Map 会先膨胀到 1 万才触发清理。单实例可接受（注释已说明扩容需迁 Redis），记录为已知限制。
