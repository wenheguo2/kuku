## 二、Server 后端（NestJS）

### 2.1 高优先级问题

| # | 文件 | 问题 | 风险 | 建议 |
|:--|:--|:--|:--|:--|
| S-01 | `config/database.config.ts` L16 | 默认密码 `kuku2026` 硬编码为 fallback；若生产环境遗漏 `DB_PASSWORD` 环境变量，将以此弱密码连接数据库 | 安全 | 生产环境启动门禁（`environment.validation.ts`）中增加 `DB_PASSWORD` 非空且非默认值校验 |
| S-02 | `modules/progress/progress.service.ts` `getOrCreate()` | 并发请求下两个请求同时发现 row 不存在→同时 create→唯一约束冲突（`child_id + word_id`）导致 500 | 稳定性 | 使用 `INSERT ... ON CONFLICT DO NOTHING` + 再查询，或加 `try/catch` 处理 QueryFailedError 后重查 |
| S-03 | `modules/progress/progress.service.ts` `summary()` | `this.progress.find({ where: { childId } })` 全量加载到内存再 filter；若孩子积累上万条进度将 OOM 或慢查询 | 性能 | 改用 `createQueryBuilder` + `SELECT subject, current_stage, COUNT(*)` 分组聚合 |
| S-04 | `modules/achievements/achievements.service.ts` `grantEligibleStickers()` | 每次读取成就列表都触发 3 学科 × 3 里程碑 × (1 查询 + 可能 1 写入) = 最多 18 次 DB 往返 | 性能 | 改为一次查出全部已有贴纸 key，内存比对后批量 insert 缺失项 |
| S-05 | `common/guards/rate-limit.guard.ts` | 内存 Map 限流，多实例部署时每个实例独立计数，实际限流阈值 = 配置 × 实例数；且 `prune()` 仅在新增 bucket 时触发，已有 bucket 过期不主动清理 | 扩展性/内存 | 注释已标注"多实例迁 Redis"；建议补充定时清理（setInterval 5min 扫描）或 LRU 策略 |

### 2.2 中优先级问题

| # | 文件 | 问题 | 建议 |
|:--|:--|:--|:--|
| S-06 | `modules/progress/quiz.util.ts` | 干扰项池为固定 10 个常用字 + 固定拼音，所有用户所有字的题目几乎相同，无区分度 | 标注为 TODO 即可；真实词库接入前建议在干扰项池中随机采样 + 按字频/偏旁生成近似干扰项 |
| S-07 | `modules/history/history.service.ts` `trim()` | 先 count → 再 find oldest → 再 remove，3 次 DB 往返；高并发下可能短暂超出 100 条 | 合并为单条 `DELETE WHERE id IN (SELECT id ... ORDER BY updated_at ASC LIMIT n)` |
| S-08 | `modules/billing/orders.service.ts` L41-46 | `if (!this.isStub()) throw` 之后紧接 `if (this.isStub() && !this.allowStub())`，第二个 `isStub()` 恒为 true（逻辑冗余） | 简化为 `if (!this.allowStub()) throw` |
| S-09 | `modules/auth/wechat.service.ts` L54 | 微信 API URL 中拼接 `secret`，若请求失败 `fetch` 抛异常时 URL 可能进入日志/监控 | 使用 URLSearchParams 构造，日志中脱敏 secret |
| S-10 | `modules/admin/admin.service.ts` `verifyPassword()` | 开发模式明文比较 `Buffer.from(devPassword)` vs `Buffer.from(password)`，虽用了 `timingSafeEqual`，但长度不等时直接返回 false 泄露长度信息 | 先 pad/hash 到固定长度再比较 |
| S-11 | `modules/parent/parent.service.ts` `detail()` | `take: 500` 硬编码上限，无分页参数；若家长需要查看全量明细则截断 | 增加 page/pageSize 参数或返回 `has_more` 标志 |

### 2.3 低优先级 / 建议

| # | 文件 | 建议 |
|:--|:--|:--|
| S-12 | `modules/progress/test-store.ts` | 内存 Map 回退模式下 `gcMem()` 仅在 `put()` 时触发；若长时间无新出题，过期 key 不会被清理。建议增加 `setInterval` 定时 GC（5min） |
| S-13 | `main.ts` | 安全头通过手写中间件实现，建议评估引入 `helmet` 包以获得更完整的头覆盖（CSP、HSTS 等），尤其后续若有 H5 页面 |
| S-14 | `app.module.ts` | `ServeStaticModule` 的 `maxAge: 86400000`（1天）对索引 JSON 偏长；索引更新后客户端可能缓存旧版。建议索引文件设 `no-cache` 或短 maxAge，音频/图片保持长缓存 |
| S-15 | 全局 | 缺少请求日志中间件（method/path/status/耗时），生产排障困难。建议接入 `morgan` 或 NestJS `Logger` 中间件 |

## 八、结论

项目代码质量整体良好，架构设计合理（模块化、守卫链、环境门禁、服务端判分），文档体系完善。主要风险集中在：

1. **生产配置安全**（数据库默认密码、支付/登录 stub 切换）
2. **并发安全**（进度 getOrCreate 竞态）
3. **性能热点**（全量加载 + 内存 filter 模式在数据增长后成为瓶颈）
4. **前端响应式细节**（非订阅式 store 读取）

建议按 P0→P1→P2 顺序分批修复，P0 项为上线硬门禁。
