## 一、严重问题（P0 — 阻塞上线/核心功能不可用）

### 1. 管理员 JWT 被全局 JwtStrategy 误拦截，后台接口不可用

**位置**：`server/src/modules/auth/jwt.strategy.ts`  
**问题**：`validate()` 中 `if (payload.role || !payload.openid || ...)` 会直接拒绝任何带 `role` 字段的 token。而管理员登录接口 `admin.service.ts` 签发的 token 包含 `role: 'admin'`，导致 `/api/v1/admin/stats` 等后台接口无法通过全局 `JwtAuthGuard`。

**风险**：
- 管理后台完全不可用（即使登录成功、携带有效 admin_token 也会被 401 拒绝）。

**修复建议**：
- 方法 A：在 `JwtStrategy.validate` 中不因为 `role` 拒绝，而是把 `role` 一并返回给 `request.user`（需确认 VipGuard 等依赖 `userId` 的守卫不受影响）。
- 方法 B：在 `admin.controller.ts` 的 `@Controller('admin')` 或 `stats` 接口上加 `@Public()`，让 `AdminAuthGuard` 自行完成管理员鉴权（推荐，与文档中“管理后台使用独立 JWT”口径一致）。

### 2. 教学播放器为纯 MOCK 实现，核心 MVP 功能缺失

**位置**：`miniapp/src/pages/growth/player/index.tsx`  
**问题**：当前教学播放器仅使用 `setInterval` 模拟时间推进，未加载真实的 `full.mp3`、`timeline.json`、`segments.json`，也未加载场景图、透明底立绘、字词信息面板等。

**风险**：
- PRD/技术架构中明确的“横屏三面板（场景+立绘+字幕+字词信息）”MVP 功能无法交付。
- 与文档中 `ED-010 ~ ED-020`、`KD-10` 等关键决策严重不符。

**修复建议**：
- 参照故事播放器 `pages/story/player/index.tsx` 实现真实数据加载流程。
- 引入 `utils/timeline.locateSegment` 做二分查找，按播放进度切换当前段。
- 加载场景图与透明底立绘，按 `characters[]` 切换角色 pose/emotion。

### 3. 综合挑战契约与文档/PRD 严重不符

**位置**：`server/src/modules/progress/progress.service.ts`  
**问题**：
1. `comprehensiveAuto` / `comprehensiveManualStart` 每字仅调用 `generateNormalQuiz(wordId, wordText)[0]`，只生成 **1 道题**。
2. `submitComprehensive` 仅校验 `answers.length !== COMPREHENSIVE_SIZE`，即只接收 **10 个答案**。

而 PRD/技术架构要求：
- 每字按学科结构出题，覆盖 1X/2X/3-9X（识字每字多题，英语每字多题）。
- 10 字综合挑战应提交多道题目答案，服务端逐字判定。

**风险**：
- 综合挑战通过标准（8/10 字通过、识字 1X+3-9X 全对、英语全对）无法在仅 1 题/字的情况下实现。
- 前端契约与后端不一致，集成时必然失败。

**修复建议**：
- 扩展 `generateNormalQuiz` 或新增 `generateComprehensiveQuiz(wordId, subject)`，为每个字生成符合学科结构的多道题目。
- 调整 `submitComprehensive` 接收 10 字 × N 题的答案结构，并逐字判定。

### 4. 普通挑战重试计数逻辑存在竞态/状态错误

**位置**：`server/src/modules/progress/progress.service.ts` 第 98-139 行

```typescript
await this.progress.save(row);          // 第一次 save
const canRetry = !passed && row.retryUsed < 1;
if (canRetry) {
  row.retryUsed += 1;
  await this.progress.save(row);          // 第二次 save
}
```

**问题**：
- `getQuiz` 中虽然重置了 `retryUsed = 0`，但 `submitQuiz` 在判定失败后没有正确给重试机会：代码在第一次 `save(row)` 之后检查 `row.retryUsed < 1`，此时仍为 0，所以 `canRetry` 为 true，但 `row.retryUsed += 1` 后第二次 save，导致首次挑战未通过即“已用掉重试”。
- 更合理的逻辑是：`retryUsed` 在 **重新生成题目时** 增加，而不是在提交时增加。

**风险**：
- 用户首次未通过即失去重试机会，与 PRD ED-028/ED-030 的“首次未通过给 1 次重试”不符。

**修复建议**：
- 将 `retryUsed += 1` 移到 `getQuiz` 中（每次生成新题时递增），`submitQuiz` 中只判断是否允许重试，不再修改计数。

## 二、中等问题（P1 — 功能缺陷/安全隐患）

### 5. 微信小程序后台音频事件订阅存在单例泄漏风险

**位置**：`miniapp/src/services/audioPlayer.ts`  
**问题**：
- `getBackgroundContext()` 在 `BackgroundAudioManager` 上绑定 `onTimeUpdate`/`onEnded`/`onError`，但事件回调只绑定一次。
- 如果 `load()` 在非 `weapp` 环境（如 H5）下创建新的 `InnerAudioContext`，旧实例没有正确移除事件监听（虽然 `destroyContext` 会调用 `destroy()`）。
- `BackgroundAudioManager` 不支持 `destroy()`，调用 `stop()` 后全局单例仍在，若后续再次 `getBackgroundContext()` 复用，时间更新事件可能残留。

**修复建议**：
- 对 `InnerAudioContext` 版本，确保 `destroyContext` 前移除所有事件监听。
- 对 `BackgroundAudioManager` 版本，统一管理播放/暂停状态同步，避免事件累积。

### 6. 小程序主题/夜间模式初始状态不正确

**位置**：`miniapp/src/stores/settingsStore.ts`  
**问题**：
```typescript
isDark: false,
isNight: false,
```
- 如果用户保存的主题是 `dark` 或系统当前是深色模式，启动时 `isDark`/`isNight` 仍默认为 `false`。
- 虽然 `app.tsx` 中调用了 `applyTheme()`，但 `applyTheme` 只在变化时 `set`，而初始值可能已导致首屏渲染错误。

**修复建议**：
- 初始化 store 时立即计算 `resolveDark(theme)` 和 `resolveNight(...)` 作为默认值。

### 7. 故事播放器字段名与文档不一致

**位置**：
- `miniapp/src/pages/story/player/index.tsx` 第 110 行
- `miniapp/src/types/content.ts` 第 145-152 行

**问题**：

**修复建议**：

### 8. 微信支付订单号高并发下可能重复

**位置**：`server/src/modules/billing/orders.service.ts` 第 48 行

```typescript
const orderNo = `ORD${Date.now()}${Math.floor(Math.random() * 1000)}`;
```

**问题**：
- `Date.now()` + 3 位随机数在高并发下可能生成相同订单号。

**修复建议**：
- 使用更可靠的唯一 ID 生成策略，例如：`uuid`、`nanoid`、或数据库序列 + 时间戳前缀。

### 9. 开发环境管理员密码比较泄露长度信息

**位置**：`server/src/modules/admin/admin.service.ts` 第 88-91 行

```typescript
const expected = Buffer.from(devPassword);
const actual = Buffer.from(password);
return expected.length === actual.length && timingSafeEqual(expected, actual);
```

**问题**：
- `timingSafeEqual` 要求长度相同，当长度不同时直接返回 false，会暴露管理员密码长度。
- 开发环境明文比较密码，安全性差。

**修复建议**：
- 开发环境也使用 scrypt 哈希，或至少固定比较逻辑，不依赖长度。

---

### 10. 限流 Guard 多实例/代理环境下不可靠

**位置**：`server/src/common/guards/rate-limit.guard.ts`

**问题**：
- 使用内存 `Map` 存储限流桶，多实例部署时不共享。
- `request.ip` 在反向代理后可能不准确（NestJS 默认不启用 `trust proxy`）。
- `prune` 只有在 `size >= 10_000` 时才清理，可能导致内存持续增长。

**修复建议**：
- 生产环境将限流迁移到 Redis 或网关层。
- 启用 `app.set('trust proxy', true)` 或读取 `X-Forwarded-For`。

---

### 11. 埋点接口可被滥用

**位置**：`server/src/modules/track/track.controller.ts`

**问题**：
- 虽然全局有 `RateLimitGuard`，但默认规则 `other` 为 100 次/分钟，埋点接口仍可能被高频调用刷数据。
- 未对 `event` 字段做白名单校验，任意字符串都可入库。

**修复建议**：
- 为埋点接口单独设置更严格的限流（如 60 次/分钟）。
- 增加 `event_name` 白名单或长度限制。

---

### 12. `auth.service.deleteAccount` 直接执行原生 SQL，存在外键/表不存在风险

**位置**：`server/src/modules/auth/auth.service.ts` 第 103-115 行

**问题**：
- 使用 `await this.dataSource.transaction(async (m) => { ... })` 直接 `DELETE FROM events/orders/memberships/...`。
- 若 `events` 表的外键约束与代码假设不一致，或某些表尚未创建，会导致事务失败。
- 未捕获异常类型，直接抛出原始错误。

**修复建议**：
- 使用 TypeORM 实体 `Repository` 或 `cascade: true` 删除，避免手写 SQL。
- 添加事务异常处理，返回友好错误信息。

## 四、安全与合规风险

### 1. 儿童信息保护
- `miniapp/src/pages/common/login/index.tsx` 虽然要求用户勾选协议，但登录后未显式提示“监护人同意”。
- 后端 `LoginDto` 强制 `guardian_consent: true`，但没有记录协议版本到 `consent_records` 表的逻辑在 `auth.controller.ts` 中校验（`auth.service.ts` 已记录，符合要求）。

### 2. JWT Secret 默认弱密钥
- `jwt.strategy.ts` 默认 `secretOrKey: 'dev_secret'`，但 `environment.validation.ts` 在生产环境会拦截。
- 如果开发者绕过环境校验或误用 development 模式部署，存在 JWT 被伪造风险。

### 3. Mock 登录共享默认账号
- `wechat.service.ts` 在 `mode === 'mock'` 且 `code` 为空时使用 `default_test_user` 作为 seed，所有未传 code 的请求会映射到同一个 openid。
- 风险：测试用户数据相互污染。

### 4. CORS 生产环境配置缺陷
- `main.ts` 中 `origin: isProduction ? corsOrigins : true`。若生产环境未配置 `CORS_ORIGINS`，则允许的 origin 为空数组，小程序请求会被拒绝；若误配置为 `true`，则允许所有来源。
- 建议生产环境强制要求配置 `CORS_ORIGINS`，为空时启动失败。

## 五、其他代码质量问题

1. **`miniapp/src/services/indexLoader.ts`**：`loadSegments` 与 `buildIndexUrl` 的 URL 编码方式不一致，可能导致中文路径编码问题。
2. **`miniapp/src/pages/story/player/index.tsx`**：收藏接口未处理 `content_id` 为空的情况；上报历史时未判断 `isLogin`。
3. **`server/src/modules/billing/orders.service.ts`**：`isStub()` 仅判断 `WXPAY_MCH_ID` 是否为空，真实商户号配置后即使未实现回调也会直接失败，符合 fail-closed 原则，但需文档化。
4. **`server/src/modules/admin/admin.service.ts` `stats()`**：`COUNT(DISTINCT user_id)` 对大表全表扫描，建议增加按日分区或索引优化。
5. **`server/src/app.module.ts`**：`ServeStaticModule` 统一 `maxAge: 86400000`，无法区分 MP3（应长期缓存）和 JSON 索引（应 24h），建议按文件类型加响应头或分路径配置。

## 七、结论

本次审查共发现 **4 个 P0 级问题**、**8 个 P1 级问题** 及若干文档/代码不一致点。其中：

- **P0 问题**集中在：管理员鉴权、教学播放器 MOCK、综合挑战契约、普通挑战重试逻辑。
- **安全层面**需关注：JWT 默认密钥、mock 登录共享账号、管理员密码比较、CORS 配置、埋点滥用。
- **文档一致性**需重点统一：`start_ms`/`end_ms` 与 `start_time`/`end_time`、综合挑战出题数量、教学播放器实现方案。

建议在 MVP 上线前优先修复 P0/P1 问题，并进行前后端集成测试。
